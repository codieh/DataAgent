## Q1. 你这个项目和普通 Text-to-SQL 最大的区别是什么？

### 我的原始回答

嗯好的。最大的区别在于完整的流程上，不仅仅是生成与执行SQL，更多地是在一些边界情况的控制，比如说高危SQL的限制，无关信息的拒绝回答、以及结果分析。

### 优化后的回答

普通 Text-to-SQL 更像是“用户提问，模型直接生成 SQL，然后执行返回结果”，链路比较短。  
这个项目的区别在于，它把数据分析请求拆成了一条完整的 Agent 工作流，不是只做 SQL 生成。

在生成 SQL 之前，它会先做意图识别，判断是不是数据分析问题；然后做 evidence/document recall 和 schema recall，把业务规则、文档定义和相关表结构先收敛出来；之后再做 query enhance，把用户的口语化问题改写成更适合生成 SQL 的形式。当前图编排里还支持在增强后做可行性评估，在 SQL 生成后做语义一致性校验。对于复杂问题，还会先做 planner，把问题拆成多步执行，而不是一条 SQL 硬做到底。

另外一个区别是可控性更强。我们不是让模型生成完就直接执行，而是加了 SQL 安全校验、敏感字段拦截、宽表导出限制、失败重试和人工审核机制，所以它更像一个可编排、可解释、可收口的 Agent 后端，而不是一个单点式的 Text-to-SQL Demo。

### 更短的面试版

最大的区别是，普通 Text-to-SQL 关注“把问题翻译成 SQL”，而这个项目关注“怎么把自然语言分析请求安全、稳定、可解释地跑通”。所以我们做的是完整工作流，包括意图识别、召回增强、Schema 聚焦、多步规划、SQL 安全执行和结果总结，而不是只有 SQL 生成这一步。

### 回答结构

这类题建议按 3 层回答：

1. 本质差异：不是单步生成，而是完整工作流  
2. 前置增强：recall / schema / enhance / planner  
3. 工程可控：安全、拒答、重试、审核、总结

### 注意事项

- 第一层一定要先回答“本质区别”，不要一上来就只讲安全限制
- “高危 SQL 限制、无关问题拒答、结果分析”是加分点，但更适合放在后半段
- 如果面试官继续追问，可以顺势展开 graph 工作流和 state 设计

## Q2. 为什么这里要用 Graph，而不是简单写几个 Service 串起来？

### 我的原始回答

Graph能更加适合复杂流程的编排

### 优化后的回答

是的，最核心的原因就是这个项目已经不是固定直线流程了，而是一个有分支、有状态、有中断恢复能力的复杂工作流，所以 Graph 比简单的 Service 串联更合适。

如果只是最基础的单轮 Text-to-SQL，其实用几个 Service 顺序调用也能做，比如意图识别、生成 SQL、执行 SQL、返回结果，这种线性链路用普通编排就够了。  
但这个项目里流程并不是一直往下走的，它会根据状态动态分支，比如：
- 意图不是数据分析时要提前结束
- schema recall 失败时要走 fallback
- planner 开启后要进入多步执行
- human review 开启后要暂停，等人工反馈再恢复
- SQL 执行失败后还可能进入 SQL repair / retry，必要时再通过人工驳回或计划校验失败回到 planner

这种场景下，Graph 的优势有三个：

第一，流程结构更清晰。节点和边可以显式表达“当前有哪些阶段、每一步之后可能去哪里”，比把大量 `if-else` 堆在一个 Service 里更容易维护。  
第二，状态管理更自然。项目里核心状态都收敛在 `SearchLiteState` 里，Graph 节点围绕状态做更新，比较适合这种 Agent 式流程。  
第三，更适合中断与恢复。比如人工审核这个点，不是一次请求里顺序执行到底，而是先停下来，等用户基于 `threadId` 提交反馈后继续执行，这种能力用 Graph 表达会更自然。

所以我会说，Graph 不是为了“炫技”，而是因为这个项目已经从普通链式调用演进成了一个可分支、可恢复、可追踪的 Agent 工作流。

### 更短的面试版

因为这个项目不是单纯的线性流程，而是一个有分支、有状态、有中断恢复的工作流。  
如果只是一条固定链路，用 Service 串起来完全可以；但这里有意图分流、schema fallback、多步 planner、人工审核、SQL retry 这些动态路径，所以用 Graph 能把节点、状态和路由关系表达得更清楚，也更适合后续扩展和维护。

### 回答结构

这类题建议按 3 层回答：

1. 先承认：简单线性流程其实不一定需要 Graph  
2. 再说明：这个项目已经出现动态分支、暂停恢复、失败回退  
3. 最后总结：Graph 更适合表达复杂 Agent 工作流

### 注意事项

- 不要把答案说成“Graph 一定比 Service 高级”
- 最好先给出一个对比：线性流程用 Service 也可以
- 一定要举出项目里的真实分支点，比如 human review、sql retry、intent 分流

## Q3. 用户发起一次查询后，这个系统内部完整经历了哪些步骤？

### 我的原始回答

一次查询后，首先会进行意图识别，分析是否是数据查询请求，如果是无关提问就提前结束；然后是一些相关内容的召回，包括相关的业务规则、用户上的文档以及数据库表信息；之后再进入规划，规划sql执行计划，然后由用户进行确认是否执行，最终得到结果后进行结果分析和展示

### 优化后的回答

一次查询进来之后，系统内部大致会走一条完整的 Agent 工作流。

第一步是入口接收和状态初始化。前端通过流式接口发起请求，后端会创建本次请求对应的 `SearchLiteState`，同时结合 `threadId` 注入多轮上下文，方便处理追问、指代和条件继承。

第二步是意图识别。系统会先判断这是不是数据分析请求，如果识别成闲聊或者无关问题，就不会继续进入 SQL 主链，而是直接收口返回。

第三步是知识与结构召回。这里会分别召回几类上下文：一类是业务规则和 FAQ 这类 evidence，另一类是说明文档和指标定义，还有一类是数据库 schema。schema 不会全量直接喂给模型，而是会先做 schema recall，筛出本次问题最相关的表和字段，减少噪声和 token 消耗。

第四步是查询增强。系统会把用户原始问题改写成更规范、更适合 SQL 生成的 canonical query，尤其是在多轮追问、口语化表达或者条件省略的场景下，这一步比较重要。

第五步是可行性评估与规划控制。对于简单问题，可以直接走 SQL 生成；对于复杂问题，会先经过可行性评估，再进入 planner，把问题拆成一个或多个 SQL 步骤。如果开启了人工审核，系统会在计划生成后暂停，等待用户确认或驳回，再决定继续执行还是回到 planner 修正计划。

第六步是 SQL 生成、语义校验与执行。系统会结合前面召回出来的 schema、业务规则、文档定义和当前计划步骤生成 SQL。生成后不会直接裸执行，而是可以先经过一层语义一致性校验，再做 SQL guard 和策略检查，比如只允许单条 `SELECT`、限制敏感字段、拦截宽表导出等，之后再通过 JDBC 执行。

第七步是错误恢复与结果总结。如果 SQL 执行失败，系统会优先围绕当前 step 做 SQL repair 或 retry；如果是人工驳回、计划校验失败这类更高层问题，才会回到 planner 修正。执行成功后，再基于结果集生成自然语言总结，并把中间过程、SQL、结果和最终总结通过 SSE 流式返回给前端。

所以从整体上看，这个系统不是“提问 -> 生成 SQL -> 返回结果”这么简单，而是“识别 -> 召回 -> 聚焦 -> 增强 -> 规划 -> 安全执行 -> 总结”的完整链路。

### 更短的面试版

一次查询进来后，系统会先初始化状态和多轮上下文，然后做意图识别，过滤掉闲聊和无关问题；接着召回业务规则、文档和相关 schema，并进一步做 schema 聚焦；之后对问题做增强，必要时先生成多步执行计划并支持人工审核；最后再生成 SQL、做安全校验、执行查询，并把结果总结后通过 SSE 流式返回给前端。整个链路本质上是一个可编排的 Agent 工作流。

### 回答结构

这类主链路题建议按 7 步回答：

1. 入口接收与状态初始化  
2. 意图识别  
3. evidence / document / schema recall  
4. query enhance  
5. feasibility / planner / human review  
6. SQL 生成、语义校验与安全执行  
7. 当前 step 局部修复与结果总结

### 注意事项

- 不要把“召回”只说成查表，还要带上业务规则和文档定义
- 最好强调 schema 不是全量塞给模型，而是先做 recall / 聚焦
- 如果提到了人工确认，最好补一句“这是可选链路，不是所有请求都必须人工确认”
- 回答结尾一定要回到一句总括：这是完整 Agent 工作流，不是单步 SQL 生成

## Q3-1. 为什么不先进行查询增强，再去做召回？

### 问题理解

这是一个流程设计上的追问，本质是在问：

- 为什么当前链路选择“先召回，再增强”
- 这种顺序是不是最优
- 有没有其他更合理的编排方式

### 优化后的回答

这是一个工程 trade-off，不是绝对不能先增强再召回，而是当前项目更偏向“带知识地增强”，所以选择了先召回、再增强。

因为这里的 `enhance` 不是单纯做文本润色，而是希望结合几类上下文一起改写用户问题，包括业务规则 `evidence`、说明文档 `document`，以及多轮上下文。这样生成出来的 `canonical query` 会更贴近真实业务语义，也更有利于后续 SQL 生成。

如果完全不先召回，增强阶段只能看到用户原始 query 和历史上下文，看不到业务术语定义、指标解释或者 FAQ 规则，这种情况下增强出来的 query 可能还是不够准，甚至会把业务含义改偏。所以当前顺序更像是：先把相关知识找出来，再基于这些知识去做更可靠的改写。

当然，先增强再召回也有明显好处，尤其适合多轮追问和口语化表达，因为它能先把“这些用户”“改成最近30天”这类不完整 query 改写成更适合检索的形式。所以更理想的做法通常不是二选一，而是拆成两层：

1. 前面先做轻量级增强，只解决多轮补全、指代消解、时间范围展开，让召回 query 更完整  
2. 后面再基于召回出来的 evidence、document 和 schema 做更强的知识增强，服务 SQL 生成

可以把当前项目理解为已经做了前半步的一部分，因为在正式召回前已经有 `multiTurnContext` 和 `contextualizedQuery` 的准备；只是没有把独立的 LLM enhance 放到 recall 之前。

### 更短的面试版

这是一个 trade-off。先增强再召回的好处是能提升 query 的可检索性，特别适合多轮追问和口语化输入；但当前项目里的 enhance 不是简单改写，而是希望结合业务规则、文档定义和 schema 上下文做更有依据的 canonical rewrite，所以我们选择了先召回、再增强。后续如果继续优化，我会考虑拆成“前置轻量增强 + 后置知识增强”两层。

### 注意事项

- 不要回答成“先增强一定更好”或“当前做法一定最优”
- 最好把问题上升到“增强是面向什么目标服务”
- 如果面试官继续追问，可以顺势讲多轮上下文和 recall query 的关系

## Q3-2. Planner 一直是动态的，为什么不考虑像 ReAct 那样的动态执行模式？

### 优化后的回答

不是不能做 ReAct，而是当前项目更偏向“受控执行的结构化规划”，所以没有走开放式的 ReAct 动态执行。

ReAct 很适合那种开放探索型场景，比如工具种类很多、路径不确定、需要 agent 边推理边试错、边调用工具边决定下一步。但这个项目的主任务相对收敛，核心还是围绕数据分析和 SQL 执行展开，虽然有多步 planner，但底层主工具基本就是 SQL，不是一个开放世界的多工具 Agent。

这个项目更强调几个工程目标：执行安全、流程可追踪、人工审核、失败收口和评测可复现。ReAct 的自由度更高，但代价是每次执行路径可能不稳定，更难做固定评测，也更难在人审、SQL 安全和状态恢复上做强约束。尤其在这个项目里，如果让模型在运行时自由尝试 SQL、自由决定下一步，会明显增加不可控性。

所以当前设计并不是不要动态，而是选择了“图上的受控动态”。比如系统已经支持：
- 根据问题动态生成 1 到多步计划
- 根据人工审核结果回到 planner 修正计划
- 根据 SQL 执行结果做 retry 或回退
- 根据当前状态决定下一节点

也就是说，它是动态的，但这种动态是被 Graph 和状态机约束住的，而不是完全放给模型自由探索。

如果后续系统演进到更多工具协同、更开放的分析任务，比如除了 SQL 还要动态调用检索、代码执行、图表分析甚至外部系统，那我会考虑把 planner 升级成更接近 ReAct 的模式。但在当前阶段，Graph + 受控 planner 更符合“稳定、安全、可解释”的目标。

### 更短的面试版

ReAct 更适合开放式多工具探索场景，而当前项目更强调稳定性、安全性和可评测性，所以我们选择了 Graph + 受控 planner，而不是让模型完全自由地边想边执行。当前系统已经有动态性，但属于“受控动态”，不是“开放动态”。

### 注意事项

- 不要把回答说成“ReAct 不好”
- 重点突出“当前阶段目标不同”
- 最好区分“受控动态规划”和“开放式动态执行”

## Q4. 为什么系统一开始要先做意图识别，而不是直接进入召回和 SQL 生成？

### 我的原始回答

意图识别是为了过滤掉一些无关问题，减少一些算力消耗，同时也是为了避免模型收到一些无关请求可能导致幻觉，错误生成SQL语句并执行

### 优化后的回答

意图识别放在最前面，核心目的是先判断这个请求值不值得进入后面的高成本数据分析链路。

第一，它能过滤掉闲聊、寒暄或者明显无关的问题，避免这些请求继续走 recall、schema 处理、SQL 生成和执行，减少不必要的算力和数据库消耗。

第二，它能降低误执行风险。如果不先做意图识别，系统可能会把一些本来不该进主链的问题也强行往 SQL 方向解释，这样就容易出现模型幻觉，生成和业务无关甚至有风险的 SQL。先做 intent classification，本质上是在前面加了一层路由和防抖。

第三，它能让整个系统的职责边界更清楚。这个项目虽然是数据分析 Agent，但并不是所有自然语言输入都应该交给 SQL 主链处理。先做意图识别，相当于把“哪些请求属于数据分析域”先划清楚，再决定是否进入后续的召回、规划和执行流程。

所以这一步不仅是为了节省算力，更重要的是减少错误路由、降低幻觉和误执行风险，让后面的链路只处理真正适合做数据分析的问题。

### 更短的面试版

因为后面的链路成本更高，也更敏感。先做意图识别可以把闲聊和无关请求提前拦住，减少不必要的召回和 SQL 生成；同时避免模型把无关输入强行解释成数据问题，从而降低幻觉和误执行风险。

### 回答结构

这类题建议按 3 层回答：

1. 节省成本：减少无效召回和 SQL 生成  
2. 控制风险：降低幻觉和误执行  
3. 明确边界：先判断是否属于数据分析域

### 注意事项

- 不要只说“节省算力”，这样会显得理由太弱
- 一定要补上“减少错误路由”和“降低误执行风险”
- 如果面试官继续追问，可以顺势展开 CHITCHAT / DATA_ANALYSIS 的分类逻辑

## Q5. 为什么这里要做多种召回：evidence、document、schema recall，而不是只把数据库 schema 给模型？

### 我的原始回答

考虑到业务可能不同，模型可能无法理解一些术语的意思或是对内部规定不熟悉，所以使用多种召回，进一步增强后续SQL生成的准确性

### 优化后的回答

核心原因是，数据库 schema 只能告诉模型“库里有什么表和字段”，但不能完整告诉模型“这些字段在业务上是什么意思、指标怎么算、内部规则怎么约束”。如果只给 schema，模型虽然知道结构，但不一定真正理解业务语义，所以很容易生成“能跑但不对”的 SQL。

所以这里把召回拆成了三类信息：

第一类是 `schema recall`，解决的是结构问题。也就是告诉模型当前问题最相关的表、字段和关系，避免把全量 schema 都塞进去，减少噪声和 token 消耗。

第二类是 `evidence recall`，解决的是业务规则问题。比如一些 FAQ、口径约定、内部规则、业务提示，这些内容往往不会体现在数据库字段名里，但会直接影响 SQL 怎么写。

第三类是 `document recall`，解决的是概念定义问题。比如术语解释、指标含义、背景文档，这些内容可以帮助模型理解“高消费用户”“GMV”“电子产品”这类业务概念到底对应什么。

所以这三类召回并不是重复的，而是分别补结构、补规则、补语义。这样后面的 SQL 生成不是只靠字段名猜，而是基于“结构 + 业务规则 + 文档定义”一起生成，准确性和稳定性都会更好。

如果只给 schema，比较容易出现三类问题：
- 表和字段选对了，但业务口径错了
- 知道字段存在，但不理解术语对应关系
- 为了弥补语义缺失，模型自己脑补规则，导致幻觉

所以从工程上看，多种召回的目的不是单纯“喂更多上下文”，而是把 SQL 生成真正依赖的不同知识来源拆开建模，再在生成前有针对性地补齐。

### 更短的面试版

因为 schema 只能提供数据库结构，不能完整表达业务语义、指标口径和内部规则。  
所以我们把召回拆成三类：`schema recall` 补结构，`evidence recall` 补业务规则，`document recall` 补术语和概念定义。这样后面的 SQL 生成不是只看字段名猜业务，而是基于结构、规则和语义一起生成，准确性会更高。

### 回答结构

这类题建议按 4 层回答：

1. 先指出 schema 的能力边界  
2. 再拆 3 类召回各自解决什么问题  
3. 再说只给 schema 会带来什么错误  
4. 最后回到目标：提升 SQL 准确性和稳定性

### 注意事项

- 不要只说“增强准确性”，要说清楚增强的是哪一类信息
- 最好强调“不是重复召回，而是不同知识源分工”
- 如果面试官继续追问，可以顺势讲 schema recall 为什么还要再做一次聚焦

## Q6. 为什么 schema 还要再做一次 recall / 聚焦，而不是把全量表结构直接给模型？

### 我的原始回答

如果全量进入上下文，这会导致一些关键信息被稀释，导致SQL后续的生成质量差。因此，项目中用的是分级召回，先召回一些关键表信息，再看命中的表的具体表结构。这种分级策略就很像claudecode中加载skill的机制，只全量加载元描述，需要时再加进一步看具体内容。分级策略很好地保护了关键语义不丢失、避免了上下文爆炸、减轻了算力消耗

### 优化后的回答

最核心的原因是，全量 schema 虽然信息更全，但对 SQL 生成来说不一定更好，反而可能让关键信息被噪声淹没。

如果把所有表、所有字段、所有外键关系一次性塞进上下文，会带来几个问题：

第一，关键信息会被稀释。模型在面对很长的 schema 时，不一定能稳定聚焦到当前问题真正相关的那几张表和几个关键字段，容易出现选错表、错连表或者抓错聚合口径的问题。

第二，上下文成本会明显上升。全量 schema 会占掉大量 prompt 空间，不仅增加 token 和算力消耗，也会挤压 evidence、document、multi-turn context 这些同样重要的信息。

第三，生成稳定性会下降。上下文一旦过长，模型更容易出现“看到了很多结构，但不知道该优先相信谁”的情况，最终生成出能跑但不够精确的 SQL。

所以这个项目里用的是一种分级聚焦的思路：先做表级 recall，筛出和当前 query 最相关的少量表；然后再基于这些表去看更细的字段、主键和外键关系，把真正有用的 schema 片段送进后续 SQL 生成。这本质上是在做“先粗筛、再细看”的上下文控制。

我觉得这个设计的价值主要有三点：
- 保护关键语义，避免相关表信息被海量无关表稀释
- 控制上下文规模，避免 prompt 爆炸
- 提升 SQL 生成稳定性，让模型更聚焦于当前问题所需的结构信息

所以 schema recall 的目标不是“减少信息”，而是“提高信息密度”，让模型看到的上下文尽量都是和当前问题强相关的。

### 更短的面试版

因为全量 schema 容易让关键信息被噪声淹没，而且会明显增加上下文成本。  
所以我们做了 schema recall，先筛出最相关的表，再聚焦这些表的字段和关系。本质上不是单纯裁剪信息，而是提升上下文的信息密度，让模型更容易生成准确、稳定的 SQL。

### 回答结构

这类题建议按 3 层回答：

1. 先说全量 schema 的问题：噪声、成本、稳定性  
2. 再说当前方案：先召回相关表，再聚焦字段关系  
3. 最后总结：不是少给信息，而是提高信息密度

### 注意事项

- 不要只说“节省 token”，这只是副作用，不是唯一理由
- “关键信息稀释”是很好的关键词，建议保留
- 类比其他系统机制可以帮助自己理解，但面试里一般优先讲项目内逻辑，避免类比过多

## Q7. 为什么在有了 recall 和 schema recall 之后，还要做 query enhance？它和 recall 不是重复的吗？

### 我的原始回答

因为召回后还是需要根据用户的输入去进行sql生成，但是用户的输入可能偏口语化，进一步进行规范可以增强模型生成的准确性。但或许以后模型足够强大时，可以忽视这种增强

### 优化后的回答

它们不是重复关系，而是解决的问题不一样。`recall` 负责补知识，`enhance` 负责补表达。

前面的 recall 和 schema recall，主要是在回答“模型应该看什么上下文”。也就是把业务规则、文档定义、相关表和字段这些外部知识补进来，解决的是信息来源问题。

但即使上下文补得很完整，用户原始输入本身仍然可能不适合直接做 SQL 生成。因为真实用户的问题经常会有几类情况：
- 表达口语化
- 条件省略
- 多轮追问里的指代不完整
- 一个问题里混着排序、过滤、统计等多个意图

所以 `query enhance` 的作用是在已有上下文的基础上，把原始 query 规范化成更适合 SQL 生成的 `canonical query`，必要时再给出一些等价改写。这样后面的 SQL 生成看到的就不是“用户怎么说”，而是“系统整理后的、结构更清晰的问题表达”。

所以可以把两者理解成两步：
- recall：先把知识找对
- enhance：再把问题说清楚

如果只有 recall，没有 enhance，模型可能“知道很多”，但还是要直接面对一个模糊、口语化、不完整的问题；  
如果只有 enhance，没有 recall，问题表达可能更规范，但模型依然缺少业务规则和 schema 语义支撑。

这两步组合起来，前者解决知识充分性，后者解决表达规范性，最终一起服务于 SQL 生成准确率。

至于“以后模型更强是不是可以不要 enhance”，我会更谨慎一点。模型能力变强后，可能会降低对显式 enhance 的依赖，但在工程系统里，是否保留这一步不只取决于模型智力，还取决于稳定性、可解释性和可控性。只要用户输入仍然存在口语化、多轮省略和表达歧义，enhance 这类显式规范化步骤通常仍然有价值，只是实现形式可能会变化。

### 更短的面试版

不重复。recall 解决的是“给模型补什么知识”，enhance 解决的是“把用户问题整理成什么表达形式”。  
前者补业务规则、文档和 schema，后者把口语化、含糊或多轮追问的问题改写成更适合 SQL 生成的 canonical query，所以一个补知识，一个补表达。

### 回答结构

这类题建议按 3 层回答：

1. 先拆分职责：recall 补知识，enhance 补表达  
2. 再说只做其中一步会有什么问题  
3. 最后回到目标：一起提升 SQL 生成准确率和稳定性

### 注意事项

- 不要把 enhance 讲成“纯润色”
- 不要轻易说“模型更强以后就不需要了”，这样容易被追问系统设计是否只是补模型短板
- 更稳的说法是：未来可能弱化，但在工程链路里仍有稳定性和可控性价值

## Q8. 为什么这里还要加 planner，多数查询直接生成 SQL 不行吗？

### 我的原始回答

如果需要多次sql语句来完成目标的话，过长的sql语句会比短的sql语句错误的概率更大，因此这里就希望通过多次生成的形式去降低错误率

### 优化后的回答

直接生成 SQL 对简单问题当然是可行的，但这个项目里加 planner，主要是为了处理那些“单条 SQL 可以勉强写，但不够稳、不够清晰、也不够可控”的复杂分析请求。

最直接的原因是，复杂问题如果强行一次生成一条很长的 SQL，错误概率会明显上升。因为这类 SQL 往往同时包含多表关联、复杂聚合、时间条件、排序、过滤，甚至还带有隐含的分步骤分析逻辑。模型一旦在其中某个局部理解错了，整条 SQL 就可能失真，调试也很困难。

所以 planner 的核心作用，就是先把复杂分析目标拆成若干更小、更清晰、更容易验证的 SQL 步骤。这样做有几个好处：

第一，降低单次生成难度。相比一次生成超长 SQL，把问题拆成多个较短步骤，模型更容易在每一步里聚焦当前目标，减少出错概率。

第二，提高可解释性。拆成 plan 之后，前端和用户都能看到系统打算先做什么、后做什么，不再是黑盒地突然吐出一条很长的 SQL。

第三，更适合人工审核和中途干预。因为一旦有 plan，用户可以在执行前确认、驳回或者要求重规划，这在单条 SQL 模式下很难做。

第四，更适合错误恢复。如果某一步执行失败，系统可以先只针对当前步骤做 SQL repair 或 retry；如果暴露出的是更高层的计划问题，再回到 planner 修正，而不是整条链路全部推倒重来。

所以 planner 的目标不是“所有请求都必须拆成多步”，而是给复杂分析场景提供一种更稳、更可控的执行方式。简单问题仍然可以单步完成，复杂问题才进入多步 planning。

### 更短的面试版

简单查询直接生成 SQL 没问题，但复杂分析请求如果强行一次生成一条超长 SQL，错误率和调试成本都会明显上升。  
所以我们加了 planner，把复杂目标拆成多个更短、更清晰的 SQL 步骤，这样既能降低生成难度，也更方便人工审核、错误恢复和结果解释。

### 回答结构

这类题建议按 3 层回答：

1. 先承认：简单问题单条 SQL 就够  
2. 再说明：复杂问题单条超长 SQL 容易出错、难调试  
3. 最后总结：planner 提供拆解、审核、恢复和解释能力

### 注意事项

- 不要回答成“planner 一定比单条 SQL 更高级”
- 一定要强调它主要服务复杂问题，不是所有问题都强制多步
- 最好补一句：planner 提升的不只是准确率，还有可解释性和可控性

## Q9. 既然有 planner，为什么还要加 human review？让系统自己执行到底不行吗？

### 我的原始回答

这是为了进一步完善系统的安全性，也是进一步匹配用户的意图（但是用户也不一定看得懂sql语句，这是个不足）

### 优化后的回答

human review 的核心目的不是替代系统能力，而是在高风险或高歧义场景下，给用户一个“最后确认和纠偏”的机会，让执行链路更可控。

第一，它可以增强安全性。即使前面已经有 intent、recall、planner 和 SQL guard，复杂分析请求里仍然可能存在理解偏差，尤其是涉及多步执行、敏感口径或者大范围数据查询时。human review 相当于在正式执行前再加一层人工把关，降低系统把“理解错但还能执行”的计划直接跑下去的风险。

第二，它可以进一步对齐用户真实意图。很多复杂需求并不是“SQL 能不能写出来”的问题，而是“系统理解的是不是用户真正想要的分析路径”。planner 给出的计划虽然是结构化的，但用户可能会觉得分析顺序不对、指标口径不对，或者希望补一个筛选条件。human review 让这种偏差可以在执行前被纠正，而不是等结果出来后再返工。

第三，它提升了系统的可解释性和信任感。对于复杂任务，用户能先看到系统准备怎么做，再决定是否继续执行，这比黑盒式地自动跑到底更容易建立信任。

当然，这个机制也有不足，你提到的那个点非常真实：用户未必看得懂 SQL。所以更合理的做法不是让用户直接审核底层 SQL，而是审核“执行计划”和“每一步的自然语言说明”。也就是说，人审更适合面向业务语义，而不是面向技术细节。当前项目里把人审放在 planner 阶段，其实也是在往这个方向靠，而不是让用户逐条看底层实现细节。

所以 human review 的本质不是“系统不够智能”，而是对于高风险和高歧义任务，引入一种可选的人在回路机制，让系统在安全性、意图对齐和用户信任之间做更好的平衡。

### 更短的面试版

因为 planner 只能说明系统“准备怎么做”，但不能保证这条路径一定完全符合用户真实意图。  
所以我们加了 human review，在复杂或高风险任务里给用户一个执行前纠偏的机会，一方面增强安全性，另一方面提升意图对齐和用户信任。更合适的审核对象也不是底层 SQL，而是 plan 的自然语言步骤。

### 回答结构

这类题建议按 3 层回答：

1. 安全：执行前再加一层人工把关  
2. 对齐：确认系统理解的分析路径符合用户真实意图  
3. 体验：提升可解释性和信任感

### 注意事项

- 不要把 human review 讲成“因为系统不够好，所以只能让人兜底”
- 你提到的“用户不一定看得懂 SQL”是个很好的反思点，建议保留
- 更稳的说法是：审核对象应尽量是自然语言 plan，而不是底层 SQL

## Q10. 既然整个项目用了 WebFlux，为什么 SQL 执行这里还是用 JDBC？这不是阻塞的吗？

### 回答思路

这题的核心不是“WebFlux 和 JDBC 谁先进”，而是：

- 项目为什么需要 WebFlux
- JDBC 阻塞会带来什么问题
- 当前项目是怎么做工程折中的

### 优化后的回答

这个项目用 WebFlux，主要不是因为数据库天然就是响应式的，而是因为它要支持 SSE 流式返回，让前端实时看到意图识别、召回、SQL 生成、执行和结果总结这些中间过程。

但数据库访问这里仍然用了 JDBC，原因更多是工程现实：JDBC 生态成熟、接入简单，而且当前项目的核心目标是先把数据分析主链稳定跑通，不一定要为了响应式而把数据库层也一起重构成 R2DBC。

确实，JDBC 是阻塞式的，所以不能直接跑在 WebFlux 的关键事件线程上。这个项目的做法是把 JDBC 调用切到专门线程池里执行，比如 `boundedElastic`，这样数据库查询虽然还是阻塞的，但不会阻塞 WebFlux 的主链线程。

所以这套设计本质上是一个工程折中：
- 上层交互和流式编排用 WebFlux
- 底层数据库先沿用成熟的 JDBC
- 中间通过线程隔离控制阻塞影响

也就是说，WebFlux 解决的是“怎么流式交互”，JDBC 解决的是“怎么稳定查库”，两者职责不同。

### 更短的面试版

WebFlux 主要是为了支持 SSE 流式交互，但数据库层当前还是沿用成熟的 JDBC。因为 JDBC 是阻塞式的，所以不能直接跑在 WebFlux 的关键线程上，这里通过 `boundedElastic` 做线程隔离。也就是说，上层用响应式交互模型，下层先保留成熟数据库方案，这是一个工程折中。

### 注意事项

- 不要把答案说成“JDBC 和 WebFlux 完全兼容无问题”
- 重点是“阻塞可以接受，但要隔离”
- 最好补一句：这是阶段性折中，不是最终唯一方案

## Q10-1. 既然 JDBC 还是阻塞的，那为什么不干脆整个项目都用 Spring MVC？

### 优化后的回答

如果这个项目只是普通查询接口，其实 Spring MVC 完全够用。

## Q11. 向量计算相似度的时候有什么优化吗？

### 当前结论

这题可以继续往很多方向展开，建议作为“召回优化专题”保留，后续单独深挖。

### 当前可回答版本

这个项目里，向量相似度本身主要还是走标准向量检索，没有自己设计新的相似度公式；优化更多是在“怎么更高效、更稳地用相似度结果”这件事上。

主要有几类优化：

1. `embedding` 预计算与复用  
   recall 文档会先补充 embedding，并存到元数据或 pgvector 表里，避免每次检索都重复计算。

2. pgvector + ANN 索引  
   项目里使用 pgvector，并创建了 `ivfflat` 索引，本质上是用近似最近邻而不是每次全量暴力比对。

3. 候选集放大  
   第一轮不会只拿最终 `topK`，而是先取更大的 candidate 集，再做过滤和排序收敛，降低误杀好结果的概率。

4. 混合召回  
   最终不是迷信纯向量分数，而是把 `BM25 + pgvector` 做融合，因为表名、字段名、术语这类场景里 lexical 信号也很重要。

5. rerank 收敛  
   在初召回之后，还会结合 coverage、exact match bonus 等特征做轻量 rerank，提升最终排序稳定性。

### 适合后续继续深挖的追问

- 为什么纯向量召回不够，还要和 BM25 混合？
- pgvector 的 `ivfflat` 是什么，有什么 trade-off？
- 为什么要先放大 candidate，再 rerank？
- 表名/字段名这类结构词，向量召回和关键词召回分别擅长什么？
- 如果数据规模继续变大，这套召回链路还能怎么优化？

## Q12. 为什么 SQL 执行前还要做 guard / policy check？只限制成 `SELECT` 不就够了吗？

### 我的原始回答

因为select也可能存在一些信息泄露的风险。比如说会把客户的一些私人信息也暴露出来，这也是应该避免直接展示的

### 优化后的回答

只限制成 `SELECT` 只能解决“不能写库、不能删库”这类最基础的安全问题，但并不能保证查询结果本身就是安全的。所以在这个项目里，`SELECT-only` 只是第一层，后面还需要 guard 和 policy check 去控制“读什么”和“读多少”。

最典型的风险有两类。

第一类是敏感信息泄露。即使是只读查询，模型也可能生成包含手机号、邮箱、身份证号、工资、银行卡等敏感字段的 SQL。如果系统直接执行并返回这些结果，本质上仍然是数据泄露，所以不能因为它是 `SELECT` 就默认安全。

第二类是大范围明细导出风险。比如 `SELECT * FROM orders` 这种语句虽然是只读的，但它可能把大量明细数据一次性导出来，风险依然很高。对于数据分析场景，很多时候用户真正需要的是统计结果，而不是整表明细，所以系统需要对这类“宽表导出”做额外限制。

所以这个项目里安全控制是分层的：
- `SELECT-only`：防止写操作、DDL、多语句
- `policy check`：拦截敏感字段查询和大范围明细导出
- `LIMIT` 与结果模式控制：避免无限制返回大量数据

这样做的目的不是单纯“防黑客”，而是防止模型在正常交互里也生成技术上可执行、但业务上不该直接放行的 SQL。

所以我会说，`SELECT` 只是“可执行性安全”的底线，但我们还需要“数据访问安全”和“业务风险控制”，这就是 guard / policy check 存在的意义。

### 更短的面试版

因为 `SELECT` 只能保证不改数据，但不能保证读出来的数据就是安全的。  
只读查询同样可能泄露敏感字段，或者一次性导出大量明细数据。所以在 `SELECT-only` 之外，还要加 policy check，去限制敏感字段访问和宽表导出，这样才能把“能执行”和“该不该执行”区分开。

### 回答结构

这类题建议按 3 层回答：

1. `SELECT-only` 只能防写操作  
2. 只读查询仍有敏感字段泄露和大范围导出风险  
3. guard / policy check 负责补齐数据访问安全和业务风险控制

### 注意事项

- 不要只说“防止 SQL 注入”，这题重点不是注入，而是只读查询本身的风险
- 你提到的“客户隐私信息泄露”是关键点，建议保留
- 最好补上“宽表导出 / 大范围明细导出”这一类风险

## Q13. SQL 执行失败以后，为什么不直接把错误返回给用户，而还要做 retry 或计划修正？

### 我的原始回答

主要是为了方便用户吧。大模型生成SQL，也会出现幻觉，导致语法错误，或者无法通过一些安全校验。也是进一步加强这个架构的鲁棒性

### 优化后的回答

直接把错误原样返回给用户当然是最简单的做法，但这个项目里之所以还要做 retry 或计划修正，是因为很多失败并不代表用户的问题本身错了，而是系统在某个中间步骤理解偏了、生成偏了，或者当前 SQL 落地方式需要调整。

最常见的失败来源有几类：
- 模型生成了语法不正确的 SQL
- 表名、字段名或 join 路径理解错了
- SQL 虽然语法正确，但不符合安全策略
- 当前这一步执行方式不合适，应该拆成更小步骤

如果系统一遇到这类问题就把底层错误直接甩给用户，用户体验会很差，而且用户往往也不知道应该怎么修。因为从用户视角看，他只是提了一个业务问题，不应该被迫理解 SQL 语法细节或者系统内部执行细节。

所以 retry 和计划修正，本质上是在做系统自愈：

第一，retry 适合处理局部可修复的问题。比如语法错误、别名问题、字段拼写偏差、安全策略提示等，系统可以把失败原因回灌给 SQL 生成阶段，再尝试生成一版更合理的 SQL。

第二，更高层的问题更适合回到 planner。比如人工审核驳回了当前分析路径，或者计划本身校验失败，这时候不是局部修 SQL 就能解决的，而要回到 planner 层修正计划。

所以这套机制的目标，不只是“方便用户”，更重要的是把很多本来会直接暴露给用户的系统级失败，尽量在系统内部吸收掉，提升端到端成功率和整体鲁棒性。

当然，这也不是无限 retry。一般都会有重试上限和失败收口逻辑，避免系统在错误路径上循环消耗资源。也就是说，这里追求的不是“永远自动修复”，而是“对可恢复失败尽量自愈，对不可恢复失败清晰收口”。

### 更短的面试版

因为很多 SQL 执行失败并不代表用户问题错了，而是系统中间生成或规划出了偏差。  
所以项目里会先尝试对可修复失败做 retry，比如语法错误、字段选择偏差、安全策略提示；如果问题更高层，比如人工驳回或计划校验失败，再回到 planner 修正。目标是把系统级失败尽量在内部吸收掉，提升端到端成功率和鲁棒性。

### 回答结构

这类题建议按 3 层回答：

1. 失败不一定是用户问题错了  
2. retry 处理局部可修复失败，planner 修正处理更高层路径问题  
3. 目标是系统自愈和提升端到端成功率

### 注意事项

- 你提到的“方便用户”是对的，但不够完整，最好升级成“系统自愈”
- 不要把 retry 讲成无限自动尝试，最好补上“有上限、有收口”
- 如果面试官继续追问，可以顺势讲 sqlRetryCount、lastFailedSql、sqlRetryReason 这些状态字段

## Q14. 为什么最后还要做结果总结，而不是把 SQL 结果集直接返回给前端？

### 我的原始回答

直接返回结果集对用户的可读性不大，作用不高

### 优化后的回答

直接返回结果集当然最原始、最客观，但对大多数业务用户来说，可读性和可用性都不够高，所以这个项目最后还会补一层结果总结。

第一，很多用户真正关心的不是“具体每一行数据长什么样”，而是“这组结果说明了什么”。尤其在聚合统计、趋势分析、TopN 排行这类场景里，用户更希望系统直接告诉他核心结论，而不是自己再去盯着表格逐行解读。

第二，结果集本身往往缺少语义解释。比如 SQL 返回了几列指标、几十行数据，技术上是正确的，但用户未必马上能看出异常点、趋势变化或者关键排序关系。结果总结可以把“数据结果”翻译成“业务结论”。

第三，结果总结能和多步 planning 更好衔接。如果前面是多步执行，单独看最后一步结果并不能完整反映整个分析过程；而总结阶段可以把多个步骤的中间发现一起串起来，形成更完整的最终回答。

第四，从产品体验上看，结果总结能把系统从“SQL 执行器”提升成“数据分析助手”。如果只把结果集直接丢给前端，系统更像一个查数工具；而有了解释和总结之后，才更像一个真正的分析 Agent。

当然，结果总结不是要替代原始结果集，而是和原始结果形成互补：
- 原始结果集保证可验证性和可追溯性
- 自然语言总结提高可读性和决策效率

所以这一步的意义，不只是“让结果更好看”，而是把查询结果转成更接近用户决策语言的输出，提高系统的业务可用性。

### 更短的面试版

因为结果集虽然客观，但对业务用户来说不一定直观。  
很多时候用户更关心“这组数据说明了什么”，而不是自己逐行解读表格。所以项目最后会补一层结果总结，把原始结果翻译成业务结论。原始结果集保留可验证性，总结负责提升可读性和可用性。

### 回答结构

这类题建议按 3 层回答：

1. 原始结果集可验证，但不够易读  
2. 总结把数据结果翻译成业务结论  
3. 原始结果和总结互补，不是互相替代

### 注意事项

- 不要只说“可读性差”，这样有点浅
- 最好补上“业务语义解释”和“决策效率”
- 可以强调：系统目标不是做纯 SQL 查询器，而是做分析 Agent

## Q15. 如果让你自己说，这个项目目前最大的不足或最想优化的地方是什么？

一是模型层面，响应速度很多程度上还是依赖于大模型的调用，如果换成本地大模型，算力足够的话，这个响应时间会大幅降低；此外模型的上下文以及模型的本身的能力也影响着整个系统。第二是召回精度，当前虽然用了BM25结合PGVector以及重排序，但是目前的这个精度还是可能存在一些遗漏。第三的就是这个结构返回，目前的结构使用了普通的文字，应该可以去做进一步的对结构的可视化分析，优化用户体验。

第一类是模型侧的时延和稳定性。目前整条链路里有多处依赖大模型调用，比如意图识别、query enhance、SQL 生成、结果总结，这会让端到端响应时间很受模型推理速度和网络调用影响。另外，模型本身的上下文能力、指令遵循能力和稳定性，也会直接影响 SQL 生成质量和结果总结效果。所以后续一个方向是继续优化模型选型和调用链路，比如更适合的模型拆分、本地化部署、缓存或者更轻量的前置模型。

## Q16. 你这个项目里，最容易出现幻觉的环节是哪几个？你分别是怎么抑制的？

### 我的原始回答

SQL生成和任务规划。SQL增加了重试机制，也通过RAG进行相关内容的召回，丰富模型的上下文。规划部分增加了，human in the loop人工反馈

### 优化后的回答

我觉得这个项目里最容易出现幻觉的环节，主要有两类：一类是 SQL 生成，一类是 planning / 高层任务拆解。如果再往前看，其实 query enhance 和 recall 选择不准也会间接放大后面的幻觉风险，但最核心的还是前两者。

第一类是 SQL 生成阶段。这里最容易出现的幻觉包括：表名或字段名脑补、join 路径理解错误、业务口径理解偏差，或者生成技术上能跑但业务上不对的 SQL。这个项目对 SQL 幻觉的抑制主要有几层：
- 先做 evidence/document/schema recall，尽量让模型不是凭空生成，而是带着业务规则、文档定义和相关 schema 生成
- 再做 schema recall，把上下文聚焦到少量相关表和字段，减少噪声
- 在生成后增加 SQL guard 和 policy check，防止模型把不该执行的 SQL 直接跑下去
- 执行失败时引入 retry，把错误原因回灌给生成阶段，尽量做局部修复

第二类是 planning 阶段。planner 的幻觉更像“高层理解偏差”，比如把用户问题拆错、分析顺序不合理、业务目标理解跑偏。这个阶段的抑制方式和 SQL 不完全一样，因为它不是简单靠语法校验能发现的。这里主要靠：
- 在 planner 前先做 query enhance 和上下文补全，减少口语化输入带来的理解偏差
- 用结构化 plan 输出，而不是自由发散式回答，降低规划漂移
- 在复杂场景下引入 human review，让用户在执行前确认或驳回计划
- 如果计划在人工审核或校验阶段暴露出高层问题，还能回到 planner 修正，而不是一条路走到底

如果再补充一层的话，我会说 recall 本身也会有“召回幻觉”的问题，准确说是漏召回或错召回。它虽然不是 LLM 直接脑补，但如果召回错了，后面模型就可能在错误上下文上做出更严重的幻觉。所以项目里才会做可切换的混合召回、类型加权、exact match bonus 和 rerank，尽量把问题控制在前面。

所以总体上，这个项目抑制幻觉的方法不是依赖单一技巧，而是把幻觉拆到不同层：
- 前面靠 recall / schema 聚焦减少“信息不足型幻觉”
- 中间靠 planning 结构化和 human review 减少“任务理解型幻觉”
- 后面靠 SQL guard、SQL repair / retry 和计划修正减少“执行落地型幻觉”

### 更短的面试版

最容易出现幻觉的主要是 SQL 生成和 planner。  
SQL 生成阶段容易脑补表字段、join 路径或业务口径，所以我们用 RAG、schema recall、语义一致性校验、SQL guard 和 retry 去抑制；planner 阶段容易把任务拆错或理解偏，所以我们用结构化 plan、human review 和计划修正去控制。整体思路是把幻觉分层处理，而不是只在最后兜底。

### 回答结构

这类题建议按 3 层回答：

1. 先点出最容易幻觉的环节  
2. 再说明各自典型幻觉表现  
3. 最后讲每一层的抑制手段

### 注意事项

- 你提到的 SQL 生成和规划是最核心的两个点，方向是对的
- 最好补一句 recall 失准会放大后续幻觉，这样答案更完整
- 不要只说“加了 RAG”，要说明 RAG 是怎么帮助减少哪类幻觉的

## Q17. 如果 recall 召回错了，后面的 enhance、planner、SQL 生成不就都会被带偏吗？你们怎么缓解这种级联错误？

### 我的原始回答

所以会引入人工反馈机制，这是一重保障。第二是SQL执行错误后，模型会自己再试，读取到了返回的错误，修复概率会增大。

### 优化后的回答

是的，recall 一旦失准，后面的 enhance、planner、SQL 生成确实都有可能被带偏，所以这个项目不能把希望只压在“第一轮召回一定正确”上，而是要做多层缓解，尽量把级联错误截断在不同阶段。

我会把缓解思路分成三层。

第一层是在 recall 前后尽量减少“带偏概率”。比如项目不是只用单一路径召回，而是支持 `BM25 + pgvector + rerank` 这种混合召回；schema 也不是全量直接喂给模型，而是先做 schema recall 聚焦相关表；另外还有 evidence/document/schema 三类不同知识源交叉补充，尽量避免因为单一召回源失准而整体跑偏。

第二层是在 planning 和执行前增加“中间纠偏”。如果问题比较复杂，系统不会立刻无脑执行，而是先输出结构化 plan；在需要的时候再引入 human review，让用户在执行前发现分析路径是不是已经偏了。也就是说，人审在这里不只是安全兜底，也是级联错误的中途拦截点。

第三层是在执行后做“失败吸收和回退修复”。如果 recall 带偏导致 SQL 生成或执行失败，系统不会立刻把底层错误直接甩给用户，而是会利用错误信息做 SQL repair 或 retry；如果暴露出的是计划层问题，再通过人工驳回或计划校验失败回到 planner 修正。这相当于在链路后半段再做一次自愈。

所以这个项目处理级联错误的思路不是“保证前面永远不出错”，而是：
- 前面尽量提高召回质量，减少带偏概率
- 中间提供人审和结构化 plan 做拦截
- 后面用 SQL repair / retry 和计划修正做失败吸收

这样即使 recall 不是 100% 准，也不会轻易让一个前置误差直接放大成最终失败。

### 更短的面试版

确实，recall 失准会带来级联错误，所以我们做的不是单点修复，而是多层缓解：  
前面靠混合召回和 schema 聚焦降低带偏概率；  
中间靠结构化 planner 和 human review 做拦截；  
后面靠 SQL repair / retry 和计划修正吸收失败。  
也就是说，不是假设 recall 永远正确，而是让系统在不同阶段都有纠偏能力。

### 回答结构

这类题建议按 3 层回答：

1. 承认 recall 失准会导致级联错误  
2. 再按前中后讲缓解机制  
3. 最后总结：目标不是零误差，而是多层纠偏

### 注意事项

- 你提到 human review 和 retry 是对的，但还少了前置的召回侧缓解
- 最好明确区分：人审偏中途拦截，SQL repair / retry 偏后置自愈，planner 修正偏高层纠偏

## Q18. 你们为什么要做 `SearchLiteState` 这种统一状态对象？每个阶段各传各的参数不行吗？

### 我的原始回答

更便于状态管理以及后续功能的新增

### 优化后的回答

可以各阶段自己传参数，但这个项目最后还是选择了统一的 `SearchLiteState`，核心原因是这条链路已经不是简单的线性调用，而是一个跨多个阶段、会分支、会回退、会恢复的工作流。在这种场景下，用统一状态对象会更稳。

第一，它更适合状态管理。这个项目里的很多信息不是某一层自己用完就结束了，而是会在多个阶段之间反复流转，比如意图结果、multi-turn context、召回结果、canonical query、plan steps、sql、retry reason、result mode 等。如果每一层都各自传参数，参数会越来越多，链路也会越来越难维护。

第二，它更适合 Graph 编排。因为 Graph 的本质就是“节点基于当前状态做更新，再决定下一步去哪”，所以统一状态对象和这种工作流模型天然匹配。每个节点只需要关注“我从 state 里读什么、我往 state 里写什么”，而不是处理很长的参数列表。

第三，它更适合失败恢复和中断恢复。比如 human review 这种场景，请求不会一次执行到底，而是中途暂停，后面再基于 `threadId` 恢复。如果没有统一状态对象，这种暂停、恢复、回退、retry 都会更难做，因为你很难完整保存和重建当时的上下文。

第四，它更适合后续扩展。新加一个阶段或者新加一个字段时，只需要在统一 state 上扩展，而不需要层层改动函数签名和节点接口。对于这种还在快速演进的 Agent 项目来说，扩展成本会低很多。

所以统一状态对象的意义，不只是“参数收敛”，更重要的是它给整个工作流提供了一个稳定的上下文载体，让编排、恢复、追踪和扩展都更自然。

## Q19. 为什么这个项目里要做多轮上下文管理？直接把用户当前 query 拿去处理不行吗？

### 我的原始回答

添加上下文，避免导致用户的query不够清晰，影响用户体验，二是对上下文的长度进行约束，这是为了模型的上下文有限考虑的、二是避免文本太长导致语义被稀释，不够清晰

### 优化后的回答

不能只看当前 query，主要是因为真实用户在多轮对话里经常不会把问题一次说完整。很多追问都会默认继承上一轮的对象、条件或时间范围，如果系统只拿当前这一句去处理，很容易理解偏。

最典型的情况有几类：
- 指代型追问，比如“这些用户里谁下单最多”
- 条件改写，比如“改成最近30天”
- 筛选补充，比如“只看电子产品”

如果没有多轮上下文管理，系统就只能把这些句子当成孤立输入处理，这样要么召回不准，要么 query enhance 和 SQL 生成都会被带偏，最终用户会觉得系统“听不懂连续对话”。

所以这个项目做多轮上下文管理，核心有两个目的。

第一，是补全语义。通过 `threadId` 维护最近几轮的用户问题、规范化 query、SQL 和结果摘要，让系统在处理追问时能知道“这些”“改成”“继续看”到底指的是什么，从而生成更完整的 contextualized query。

第二，是控制上下文长度。多轮信息不是越多越好，如果把所有历史都无限塞给模型，不仅会增加 token 成本，还会让关键信息被旧上下文稀释。所以项目里只保留最近有限轮次，并对字段长度做截断，本质上是在做“有边界的上下文记忆”，既保证连续性，也避免上下文膨胀。

所以多轮上下文管理的意义，不只是让系统“记住聊天记录”，而是让它在连续分析场景里既能理解追问，又不会因为上下文过长而失焦。

### 更短的面试版

因为真实用户的追问往往不是完整句，而是默认继承上一轮对象、条件或时间范围。  
如果只处理当前 query，系统很容易理解偏。所以项目里会基于 `threadId` 管理最近几轮上下文，用来补全追问语义；同时又会限制保留轮数和字段长度，避免上下文无限膨胀、语义被稀释。

### 回答结构

这类题建议按 3 层回答：

1. 先说为什么只看当前 query 不够  
2. 再说多轮管理解决什么问题：语义补全

## Q20. 为什么 evidence、document、schema 要分三类存和召回？把它们统一成一种知识源不行吗？

### 我的原始回答

各种来源的重要程度是不一样的，比如说SQL就很依赖表的信息，理解一些关键词需要一些业务信息，但是表信息更重要，决定着是否SQL正确

### 优化后的回答

可以统一成一种知识源去存，但这个项目最后还是把 evidence、document、schema 分开建模和召回，主要是因为它们在语义角色、重要程度和后续使用方式上都不一样。如果硬合成一类，系统虽然更简单，但控制力会变弱。

最关键的区别在于，这三类知识解决的问题不同。

`schema` 是结构约束，决定的是 SQL 能不能写对。表、字段、主外键关系这些信息是 SQL 生成的硬边界，如果这里错了，后面 SQL 基本就不成立。所以 schema 在整个链路里通常是优先级最高、约束最强的一类知识。

`evidence` 更像业务规则和 FAQ，解决的是口径和规则问题。比如某个指标怎么算、哪些状态该过滤、某些术语在业务里怎么理解，这些内容不一定直接体现在表结构里，但会影响 SQL 的写法和过滤条件。

`document` 更偏概念定义和背景说明，解决的是术语理解和语义补充问题。比如“高消费用户”“电子产品”“GMV”这类词到底指什么，往往需要文档来补足。

所以把它们拆开有几个好处：

第一，召回策略可以更有针对性。schema 更强调结构命中，evidence 更强调业务规则匹配，document 更强调概念和语义补充。如果强行混在一起，排序标准会更模糊。

第二，后续使用方式不同。schema 是 SQL 生成时的硬约束，evidence 和 document 更像软约束和语义提示。如果全部混成一类，模型不容易区分“哪些信息必须服从，哪些信息只是辅助理解”。

第三，便于做优先级控制和调试。分开之后，可以更清楚地分析到底是结构召回错了、业务规则缺了，还是术语理解偏了，后续优化也更有方向。

所以我的理解是，这种拆分不是为了把系统做复杂，而是为了让不同类型的知识在召回、排序和生成阶段都保持清晰分工。尤其在 SQL 场景里，schema 确实通常是最硬的边界，业务知识和文档知识是在这个边界之上做补充。

### 更短的面试版

因为这三类知识的角色不一样。

### Q-Prompt-1. 你是如何设计提示词的？

#### 优化后的回答

我在这个项目里设计提示词时，核心不是追求“写一段很长很聪明的话”，而是把 prompt 当成工作流里的接口协议来设计。因为这个系统不是单次聊天，而是一个多阶段 Agent 链路，所以不同阶段的 prompt 目标不一样，我更关注的是任务边界清晰、上下文结构稳定、输出格式可消费。

整体上，我会先按阶段拆 prompt，而不是一个大 prompt 做到底。比如意图识别、Query Enhance、Planner、SQL 生成、结果总结都会分别设计。这样做的好处是每个阶段只做一件事，模型不容易漂移，也方便单独调试和评测。

每一类 prompt 我通常会明确三件事：

1. 当前阶段的任务边界  
2. 输入上下文的来源和优先级  
3. 输出格式约束

比如在 SQL 生成阶段，我会明确 schema 是硬约束，evidence/document 是辅助知识；在 planner 阶段，我会要求输出结构化 plan JSON；在意图识别阶段，我会把任务压缩成一个窄分类器，而不是泛助手。

所以我对 prompt 的理解不是“让模型自由发挥”，而是“让模型在每一步按协议完成一个清晰的子任务”。另外我也不会把安全完全押在 prompt 上，对于高风险阶段，后面还会配合 SQL guard、policy check、SQL repair / retry 和计划修正做后置控制。

#### 更短的面试版

我设计 prompt 的核心不是写得多花，而是让它在工作流里稳定可控。  
具体来说，我会按阶段拆 prompt，每个阶段只做一件事；把 evidence、document、schema 等上下文分区组织，并明确优先级；同时严格约束输出格式，让结果能被后续程序稳定消费。对于 SQL 生成这类高风险环节，prompt 只是前置约束，后面还会配合 guard 和 policy check 做后置兜底。

### Q-Prompt-2. 你们项目里的各类 prompt 是怎么设计的？请举例说明

#### 1. 意图识别 Prompt

对应代码：
- `IntentMinimaxStep`

目标：
- 判断用户输入是不是数据分析请求

设计重点：
- 角色很窄：只做分类，不做回答
- 分类边界明确：`DATA_ANALYSIS` vs `CHITCHAT`
- 对多轮追问做保守放行
- 输出固定 JSON

举例：
- 用户输入“这些用户里谁下单最多”
- prompt 会结合多轮上下文提示模型：如果上文属于数据分析，则这种追问仍应归为 `DATA_ANALYSIS`

总结：
- 这个 prompt 的重点不是“聪明回答”，而是“稳定做窄任务分类”

#### 2. Query Enhance Prompt

对应代码：
- `EnhanceMinimaxStep`

目标：
- 把用户原始 query 改写成更适合 SQL 生成的 `canonicalQuery`

设计重点：
- 保持原意，不新增业务要求
- 保留时间范围和过滤条件
- 使用 `multiTurnContext + evidence + document`
- 输出结构化 JSON：`canonicalQuery` + `expandedQueries`

举例：
- 原 query：“这些用户里谁下单最多”
- 增强后的 query 会显式补上上一轮上下文和分析对象，变成更完整的表达

总结：
- 它不是单纯润色，而是面向 SQL 生成的语义规范化

#### 3. Planner Prompt

对应代码：
- `SearchLitePlannerGraphNode`

目标：
- 把复杂问题拆成结构化执行计划

设计重点：
- 强约束输出 JSON plan
- 限制工具类型只能是 `SQL`
- 限制步数
- 每一步必须可执行
- 如果前次规划失败，要显式修复

举例：
- 用户问题：“统计每个分类的销售额，并找出销售额最高的分类”
- planner 会拆成一组更清晰的 SQL 步骤，而不是自由发散描述

总结：
- 核心不是“聪明拆任务”，而是“拆成可执行、可审核、可回退的结构化计划”

#### 4. SQL 生成 Prompt

对应代码：
- `SqlGenerateMinimaxStep`

目标：
- 生成可执行、尽量正确且安全的 SQL

设计重点：
- 只允许输出单条 SQL
- 不要 markdown / 不要解释 / 不要 JSON
- 明确上下文来源：schema、evidence、document、retry hint、plan context
- 明确优先级：schema 是硬约束
- 明确安全约束：只读、避免敏感字段、避免 `SELECT *`、尽量加 `LIMIT`

举例：
- 用户问题：“查询购买过智能手机的用户”
- prompt 会把模型约束到真实结构、辅助知识和单条 SQL 输出协议上

总结：
- SQL 生成 prompt 更像受控接口协议，而不是普通聊天 prompt

#### 5. 结果总结 Prompt

对应代码：
- `ResultMinimaxStep`

目标：
- 把 SQL 结果集翻译成业务用户更容易理解的结论

设计重点：
- 输入是结构化的：问题、SQL、row count、preview rows、plan summary
- 输出要求明确：中文、简洁、基于数据、说明模式
- 对失败和空结果场景做特殊处理

举例：
- 如果结果是每日订单趋势，prompt 会引导模型总结波动、峰值和关键变化，而不是简单复述表格

总结：
- 目标是把“机器可验证的结果集”转成“业务用户可消费的结论”

#### 总结

这个项目里不同 prompt 的分工很清楚：
- 意图识别：决定是否进入主链
- Query Enhance：整理问题表达
- Planner：拆解复杂任务
- SQL Generate：受控生成可执行 SQL
- Result Summary：翻译业务结论

所以 prompt 设计的本质不是“写一段很强的话术”，而是让模型在不同阶段稳定完成不同职责。

## RAG 专题

### Q-RAG-1. 你这个项目为什么需要 RAG？如果不做 RAG，只给模型数据库 schema，让它直接生成 SQL，不行吗？

#### 我的原始回答

有一些业务知识，，召回后可以帮助模型去进行理解，更加精准地生成SQL

#### 优化后的回答

只给模型数据库 schema，确实能让它知道“有哪些表、哪些字段”，但很多情况下这还不够，因为 SQL 生成不仅依赖结构信息，还依赖业务语义、术语口径和内部规则，所以项目里才需要 RAG 来补这部分缺失知识。

最典型的问题是，schema 只能回答“数据库里有什么”，但回答不了“这些字段在业务上怎么理解、指标怎么算、哪些状态要过滤、某个术语对应什么概念”。如果没有这类知识，模型虽然可能生成一条语法正确的 SQL，但很容易出现业务口径错误，或者在复杂场景下靠猜测去补全逻辑，从而产生幻觉。

所以这个项目里的 RAG，本质上是在给 SQL 生成补三类信息：
- 业务规则，比如口径、过滤条件、FAQ
- 文档定义，比如术语解释、指标含义、背景说明
- 相关结构信息，比如当前问题真正相关的表、字段和关系

这样模型生成 SQL 时，不是只看字段名去猜业务，而是带着“结构 + 规则 + 语义”一起生成，准确性会更高，复杂查询场景下也更稳。

所以如果不做 RAG，系统也许在简单问题上还能工作，但一旦碰到业务术语、隐含规则、多轮追问或者口径敏感场景，SQL 质量和稳定性都会明显下降。

#### 更短的面试版

因为 schema 只能告诉模型数据库里有什么，不能完整告诉它业务规则、术语定义和指标口径。  
这个项目做 RAG，本质上是给 SQL 生成补业务语义，让模型不是只看字段名猜业务，而是基于结构、规则和语义一起生成 SQL，所以复杂场景下会更稳。

#### 回答结构

这类题建议按 3 层回答：

1. 先承认：只给 schema 在简单场景下可以工作  
2. 再指出：schema 无法覆盖业务规则和术语语义  
3. 最后总结：RAG 是在给 SQL 生成补业务上下文

#### 注意事项

- 你说“帮助模型理解业务知识”这个方向是对的
- 最好不要只停留在“更精准”，要说清楚精准的是哪部分：业务规则、术语、口径
- 很适合强调：schema 解决结构，RAG 解决语义和规则
