# 智能销售数据分析 Agent：校招面试问题与参考回答

> 本文依据当前 Python 后端代码整理。回答以“我为什么这样设计、代码如何工作、目前还有什么不足”为主，不建议逐字背诵。面试时先给结论，面试官继续追问后再展开实现细节。

## 一、先校准简历与代码事实

### 1. 这份项目最准确的一句话定位是什么？

这是一个面向电商销售数据的自然语言分析 Agent。用户提出销售额、订单趋势、商品表现或库存等问题后，Agent 会按需检索数据库和业务信息生成 SQL，执行查询；支持调用隔离的 Python 环境进行大数据结果的分析，最后返回文字结论、指标和图表配置。

### 2. 简历中说“采用 ReAct 思想”准确吗？

准确，但我会解释成“ReAct 式工具循环”，而不会说完全照搬某篇论文。核心循环是：模型根据当前问题和已有观察决定下一步工具，工具结果以 `ToolMessage` 回到上下文，模型再决定继续检索、执行 SQL、做 Python 分析还是结束。LangGraph 负责循环和确定性安全节点，模型不能绕过 SQL 校验直接访问数据库。

### 3. 这个项目能称为 Agentic RAG 吗？

可以。传统 RAG 通常在生成前固定执行一次检索，本项目把 `search_schema`、`retrieve_knowledge`、历史结果查询等能力注册为工具，由 Agent 根据任务主动选择检索时机，并可根据结果再次检索。它的 Agentic 体现在“检索是决策循环中的动作”，不只体现在使用了向量数据库。

### 4. 简历中的“用户长期记忆”目前完全接入主链了吗？

需要谨慎回答。当前在线生效的长期能力主要是：用户明确要求“记住”时，Agent 调用 `rewrite_core_memory` 改写核心记忆，新会话会把这份核心记忆作为隐藏 System Message 注入。长期记忆自动抽取器、向量检索和 TTL 淘汰代码已经实现并有单元测试，但还没有接入每次运行的主执行链。因此口述时应说“核心记忆与历史检索”，不能声称每轮都会自动沉淀并召回长期记忆。

### 5. 当前有没有独立的意图识别节点？

没有。现在普通对话、数据分析、历史查询和记忆管理统一由 `agent_decide` 结合原生 Tool Calling 决定。这样减少了一次固定 LLM 调用，也避免意图分类错后把后续路径彻底分错。运行完成后，系统会根据实际调用过的工具把行为归类为数据分析、历史查询、记忆管理或普通对话，但这是事后统计，不是执行前路由。

### 6. RAG 中有没有独立 rerank 模型？

当前没有 Cross-Encoder 或 LLM reranker。项目使用的是 BM25 与 Chroma 向量召回，再用 RRF 按名次融合。简历里应写“RRF 融合排序”，不要写“rerank 模型”或“语义重排模型”。

## 二、项目介绍与整体架构

### 9. 请用一分钟介绍项目。

面向电商销售的数据分析 Agent。我把表结构检索、业务知识检索、SQL 提交、历史结果查询和 Python 分析封装成工具，由模型在 LangGraph 中循环决策，避免让模型只凭一段数据库描述直接生成 SQL。SQL 执行前必须经过 SQLGlot AST 校验和可选人工审核，完整结果保存为 CSV，SQLite 只存运行状态和结果预览，前端通过 REST 获取快照、通过 SSE 接收可恢复的过程事件。项目主要解决表字段幻觉、长会话上下文和生成内容的安全执行问题。

### 10. 如果面试官允许讲三分钟，应该怎么展开？

我会按一条请求的数据流展开。FastAPI 接收请求后先创建会话消息和 Run，后台任务读取 SQLite 中的近期消息与摘要，构造 LangGraph 初始状态。图先做输入注入检查，再进入 Agent 工具循环。模型通常先检索实时 MySQL Schema，必要时检索业务指标口径，再提交候选 SQL。候选 SQL 不由工具直接执行，而是经过 SQLGlot 的只读、表字段白名单、敏感字段和 LIMIT 等检查，通过后才进入 MySQL。查询结果全量写 CSV、预览写 SQLite，复杂分析可把 CSV 只读挂载给 Docker 中的 Python。最终模型根据全部结果集生成结构化总结、指标和图表。全过程被记录为阶段、工具调用、产物和事件，前端断线后也能继续读取。

### 12. 为什么选择 LangGraph，而不是自己写 while 循环？

用LangGraph主要是因为项目中涉及到一些状态的合并，以及节点状态的中断和恢复。用LangGraph会更加方便一些，因为它有个提供状态图条件边，对于状态转移会更加便捷。



### 14. 一条请求从进入后端到返回结果，完整流程是什么？

1. `POST /conversations/{id}/runs` 创建 Run，并把用户问题写入 SQLite。
2. `TaskRegistry` 创建后台 `asyncio.Task`，接口立即返回 202 和 SSE 地址。
3. 执行器读取历史消息，必要时做滚动摘要，构造初始 `AnalysisState`。
4. `input_guard` 检查提示注入。
5. `agent_decide` 调用 LLM，模型按需调用工具。
6. `search_schema` 从 MySQL 读取实时 Schema 并做混合召回；`retrieve_knowledge` 检索业务文档。
7. `execute_sql` 只提交 SQL，随后由 `sql_validate` 做确定性检查。
8. 如果启用人工审核，图在 `human_feedback` 中断；审批后用 checkpoint 恢复。
9. `sql_execute` 只读执行 SQL，结果写 CSV 和 SQLite 预览。
10. Agent 可以继续执行更多 SQL、查询历史结果或调用 Python 分析。
11. `result` 汇总所有结果集，生成结构化分析。
12. 执行器持久化阶段、工具调用、产物与事件，SSE 端点把事件增量推给前端。

### 15. `AnalysisState` 是什么？为什么不用普通全局变量？

`AnalysisState` 是 LangGraph 节点之间共享的显式状态契约，包含问题、消息、Schema、知识、SQL、安全结果、查询结果引用和迭代计数等。节点只返回状态增量，LangGraph 负责合并，其中 `messages` 使用 `add_messages` reducer。它和全局变量的区别是状态与具体 Run 绑定、可以 checkpoint、可以回放，也不会依赖线程局部变量。

### 16. `run_id`、`conversation_id` 和 LangGraph `thread_id` 有什么区别？

`conversation_id` 表示用户会话，可包含多轮 Run；`run_id` 表示一次分析任务；当前实现把 `run_id` 同时用作 LangGraph 的 `thread_id`。因此 checkpoint 主要服务单次 Run 的人工审核恢复，不负责跨 Run 直接延续对话。跨轮上下文由 SQLite 消息、摘要和历史检索负责。

### 17. 为什么不把 `conversation_id` 直接作为 LangGraph `thread_id`？

如果多个 Run 共用一个 `thread_id`，并发请求、重试和人工审核容易覆盖同一图状态。当前按 Run 隔离 checkpoint，可以明确知道恢复的是哪次任务；会话连续性在图外由持久化消息构建。缺点是每次 Run 都要重新投影会话上下文，不能直接继承前一次图中的临时工具状态。

### 18. 为什么同时需要 LangGraph State、SQLite 业务表和 checkpoint？

三者用途不同。Graph State 是当前运行中的工作内存；checkpoint 保存图执行位置和状态快照，支持中断恢复；SQLite 业务表保存会话、消息、Run、阶段、工具调用、产物和结果引用，面向 API 查询、审计和前端展示。只保存 checkpoint 不方便做业务查询，只保存业务表又不能直接恢复图的执行栈。

### 19. 为什么还要定义 Artifact？

节点状态适合驱动流程，不适合作为稳定前端契约。Artifact 把计划、Schema 召回、SQL 预览、查询结果和最终分析等阶段产物独立持久化，前端可以按类型展示和回看，也便于审计某个结论来自哪次工具或哪份结果集。

### 20. 为什么创建 Run 返回 202，而不是等待分析完成？

LLM、数据库和 Python 分析可能持续几十秒。同步等待会占用请求连接，也不便于取消、审核和断线恢复。接口只负责受理并返回 Run ID，执行由后台 Task 推进，客户端通过 Run 快照和 SSE 观察状态。

## 三、ReAct、Tool Calling 与 LangGraph

### 21. ReAct 在项目中具体体现在哪里？

`agent_decide` 把历史、Schema、业务知识、活动结果和观察投影给模型；模型通过原生 Tool Calling 选择一个动作；ToolNode 执行工具并返回 `ToolMessage`；图再回到 `agent_decide`。SQL 执行后也回到 Agent，让它基于真实结果决定继续查数据、做 Python 分析或结束，形成“决策 → 行动 → 观察 → 再决策”的循环。

### 22. 为什么每轮最多调用一个工具？

项目把 `parallel_tool_calls` 设为 `False`，系统提示也要求每轮一个工具。这样能够保证依赖顺序，例如先拿 Schema 再写 SQL、先有 SQL 结果再做 Python 分析；同时便于把每一步持久化、审核和定位错误。代价是独立检索不能并行，复杂任务的 LLM 往返次数会增加。

### 23. 为什么使用 OpenAI 原生 Tool Calling，不让模型输出 JSON 动作协议？

原生 Tool Calling 的工具名和参数由 JSON Schema 约束，SDK 会把工具调用与普通文本分开，LangGraph ToolNode 也能直接处理。手写 JSON 协议需要自己从 Markdown 或混杂文本中提取动作，格式错误和提示注入风险更高。项目仍会对工具参数做 JSON 解析和类型校验，不能把协议约束当成业务安全校验。

### 24. 工具是如何注册给模型的？

工具使用 LangChain 的 `@tool` 定义。`AnalysisToolRegistry.specifications()` 读取 `tool_call_schema` 生成公开参数，再由 OpenAI 客户端包装成标准的 `{"type":"function","function":...}`。`InjectedState` 和 `InjectedToolCallId` 由运行时注入，不会暴露给模型，避免模型把完整状态作为参数回传。

### 25. 当前有哪些主要工具？

包括更新分析计划、请求澄清、检索 Schema、查看完整表结构、检索业务知识、提交 SQL、搜索分析历史、读取历史结果、搜索和读取其他会话、Python DataFrame 分析，以及显式改写核心记忆。工具的共同特点是模型只能表达意图，真正的数据访问和安全控制由后端完成。

### 26. `execute_sql` 工具为什么不直接执行 SQL？

如果工具直接执行，模型一旦选中它就可能绕过后续安全步骤。当前工具只把候选 SQL 写入状态并设置 `pending_sql_validation`，图必须进入 `sql_validate`，通过后才可能审核和执行。这把概率性的模型决策与确定性的安全边界隔开了。

### 27. Agent 如果还没检索 Schema 就直接生成 SQL，怎么办？

`agent_decide` 有后端护栏：当前状态没有 Schema，而模型选择 `inspect_tables` 或 `execute_sql` 时，系统会把动作改写成 `search_schema`。这条规则不依赖提示词，即使模型不遵守“先查 Schema”的提示，也不能直接执行。

### 28. 工具失败后如何重试？

工具或 SQL 执行失败会形成带 `ok`、`error` 和 `retryable` 的 observation，回到 Agent 上下文。模型可以根据错误修改 SQL或选择其他工具。SQL 校验还有修复次数计数；超过上限会进入 `sql_repair_exhausted`。目前默认修复上限 50 偏大，合理做法是按任务复杂度设为 2 到 3 次并加入总 Token/时间预算。

### 29. 为什么既有 Prompt 约束，又有代码护栏？

Prompt 用来告诉模型怎样高效行动，例如什么时候检索知识、何时澄清；代码护栏负责不能被模型绕过的约束，例如无 Schema 禁止执行、SQL AST 校验、循环次数、结果行数和沙箱权限。Prompt 是软约束，后端策略和数据库权限才是硬边界。

### 30. `tools_condition` 做了什么？

它查看 `agent_decide` 返回的最后一条 AIMessage。如果包含工具调用就路由到 `tools`，没有工具调用就进入最终结果节点。它只判断“有没有工具”，具体工具行为由 ToolNode 和后续条件边处理。

### 31. 人工审核如何中断和恢复？

SQL 通过安全检查后，如果 Run 开启审核，`human_feedback` 调用 LangGraph `interrupt`，checkpoint 保存当前状态和执行位置。执行器把 Run 标记为 `waiting_review` 并创建 Review 记录。用户审批后，后端用同一个 `run_id/thread_id` 调用 `Command(resume=...)`，图从中断点继续；驳回时把意见写回计划，再回到 Agent 决策。

### 32. Checkpoint 是否意味着服务重启后所有任务都自动续跑？

不是。它支持人工审核期间的状态恢复，但当前启动补偿逻辑会把重启前处于 `queued/running` 的任务标记为 `service_restarted` 失败，让用户重试，并没有自动重新调度。面试时要区分“图中断恢复能力”和“进程崩溃后的任务自动恢复能力”。

### 33. 为什么不让模型输出完整思维过程？

系统只要求工具调用前返回简短决策依据，不保存隐藏推理。实际可观测性来自工具名称、参数、结果、阶段耗时和最终产物。这样既能调试行为，也避免把不可控的长推理当成系统事实或暴露内部提示。

### 34. Agent 什么时候调用 Python 分析？

提示词要求先有 SQL 真实结果，且任务涉及趋势、同比环比、异常、相关性或多结果集合并时才调用 `analyze_dataframe`。简单聚合优先在 SQL 中完成，因为数据库更擅长过滤和聚合，传输数据也更少。

### 35. 什么时候应该请求用户澄清？

项目把澄清设为最后手段。只有已经检索 Schema 和业务知识，仍缺少无法合理推断的决定性条件，而且继续执行会改变核心意图或产生安全风险时才询问。普通展示格式、排序方向、Top N 等有默认值，不应频繁打断用户。

### 36. 这个 Agent Loop 会不会无限循环？

代码有最大 Agent 轮数、Schema 搜索次数、SQL 执行次数和 SQL 修复次数，并把剩余预算放进模型上下文。达到上限后强制结束。不过当前默认值都为 50，工程上虽然有边界，但成本控制仍不理想，应该增加总耗时、总 Token 和分级任务预算。

## 四、RAG 与 Schema 召回

### 37. 项目为什么需要两类 RAG？

一类是实时 Schema 召回，回答“应该查哪些表、有哪些字段、如何关联”；另一类是业务知识召回，回答“销售额、GMV、退款率等指标按什么口径计算”。Schema 是结构事实来源，业务文档是语义和规则来源。二者不能互相替代，业务文档不能凭空创造数据库字段。

### 38. 为什么不能直接把完整 Schema 放进 Prompt？

小型演示库当然可以，但表和字段增加后会占用大量上下文，增加模型选错表和注意力分散的概率。项目先把每张表转成可检索文档，按问题召回少量表，再扩展必要关联表；完整 Schema 仍保存在状态中，需要时可以通过 `inspect_tables` 查看。

### 39. Schema 文档是怎样构造的？

系统实时读取 MySQL 中的表名、字段名、字段类型、注释和外键，把每张表转成一条检索文本，例如“数据表 orders；字段 order_date、total_amount、status；外键 user_id 关联 users.id”。BM25 和向量检索都基于这段文本，因此用户说中文业务含义、英文表名或字段名都有机会命中。

### 40. Schema 召回的具体参数是什么？

当前先返回 `recall_schema_top_k=4` 个检索命中，再按直接外键关系扩展邻居，总表数不超过 `recall_schema_max_tables=8`。这不是“最多四表联查”，因为关联扩展后最多可以保留八张表，Agent 还可以调用 `inspect_tables` 补充指定表。

### 41. 为什么要做外键邻居扩展？

用户问“购买过某类商品的用户”时，语义上容易命中 users 和 products，但真正 SQL 还需要 orders 与 order_items 作为连接链路。如果只保留语义最相似的表，会漏掉中间表。当前做一跳双向外键扩展，以少量额外上下文换取 Join 路径完整性。

### 42. 一跳邻居扩展有什么不足？

它可能把与问题无关但直接关联的表也带进来，而且跨两跳以上的路径不一定完整。更成熟的方案是把 Schema 建成关系图，在召回种子表后求最小连接子图，并把语义分数、连接成本和表数量一起优化，而不是对每个命中表无差别加一跳邻居。

### 43. BM25 如何计算？

代码使用标准 Okapi BM25：

`score = IDF(t) * f(t,d) * (k1+1) / (f(t,d) + k1 * (1-b+b*|d|/avgdl))`

其中 `k1=1.5` 控制词频饱和，`b=0.75` 做文档长度归一化，IDF 使用平滑公式 `log(1 + (N-df+0.5)/(df+0.5))`。只有分数大于 0 的文档才进入结果，因此无关查询不会为了填满 Top-K 强行返回文档。

### 44. 中文 BM25 如何分词？

英文、数字和下划线标识符用正则切分并转小写；连续中文同时产生单字和相邻二字 bigram。例如“销售额”会生成“销、售、额、销售、售额”。它实现简单，能兼顾字段标识符和中文短语，但不理解同义词，正是向量召回要补充的部分。

### 45. 向量召回如何计算分数？

Chroma 集合使用 cosine 距离。代码把相似度计算为 `1 - distance`，低于 `recall_vector_min_score=0.25` 的候选直接丢弃。这个 0.25 是经验阈值，不应宣称适用于所有 embedding 模型；模型更换后应重新通过验证集调参。

### 46. 为什么 BM25 分数和向量分数不能直接相加？

BM25 分数没有固定上界，向量相似度通常落在有限区间，数值尺度完全不同。直接相加会让其中一个分支长期占优。项目使用 RRF，只依赖各分支内部排名，不要求分数归一化，因此更稳定也更容易解释。

### 47. RRF 的公式是什么？

每个候选在一个排序分支中的贡献是 `1 / (k + rank)`，当前 `k=10`。同一文档在 BM25 和向量两个分支都出现时贡献相加，再按总分排序。比如某文档在 BM25 排第 1、向量排第 3，得分是 `1/11 + 1/13`；只在一个分支排第 1 的文档只有 `1/11`，因此双路稳定命中会更靠前。

### 48. RRF 的 `k` 有什么作用？

`k` 越小，头部名次差异影响越大；`k` 越大，前几名的差距被压平。当前设为 10，比常见的 60 更强调头部排序。是否合适需要通过真实查询集调参，不能只凭经验判断。

### 49. 候选集和最终 Top-K 如何设置？

每个分支先取 `top_k * recall_candidate_multiplier`，当前倍率为 4，再做 RRF，最终截断到 Top-K。业务文档默认返回 5 条，Schema 初始返回 4 张表。扩大候选是为了增加两个分支交集，但倍率太大也会增加向量查询和融合开销。

### 50. 为什么同时保留表级和字段级信息？

当前检索单元是表，但表文档内容包含字段名、类型、注释和外键，所以检索时字段也参与匹配。命中表后，状态中保存其字段详情，SQLGlot 再用这些字段做白名单。严格来说这不是独立的“字段级二次召回模型”，面试时不要把它说成两套完整检索器。

### 51. 业务知识如何切块？

Markdown 先按一到四级标题拆成有标题路径的章节，再按空行保留自然段落。段落不超过 512 token 时作为完整 Chunk；只有超长段落才使用递归分隔符，优先按空行、换行、句号、分号、逗号和空格切分，并保留 64 token overlap。标题路径会拼到正文前作为 embedding 与检索文本。

### 52. 为什么按 Token 而不是字符切块？

模型和 embedding 接口的限制按 Token 计算，中英文字符和 Token 比例不同。使用与 embedding 模型匹配的 `BAAI/bge-m3` tokenizer 能更准确控制 Chunk 大小，避免中文段落按字符看不长、实际却超过模型输入限制。

### 53. 为什么 overlap 只用于超长段落？

标题和自然段落本身已经提供语义边界，对每个 Chunk 都重叠会产生大量重复向量，检索结果也可能被同一段内容占满。只有一个语义单元被迫拆开时，边界附近的信息可能丢失，此时 64 token overlap 才有价值。

### 54. 如何做增量索引？

SQLite manifest 保存源文件哈希和每个 Chunk 的记录。索引命令扫描 Markdown/TXT：哈希未变化就跳过；文件变化则重新切块、upsert 新向量并删除失效 Chunk；源文件删除时同步清理 Chroma。Chunk ID 绑定文档 ID、序号和内容哈希，使内容变化后能得到稳定的更新行为。

### 55. 为什么离线建文档索引，不在每次请求时切块和 embedding？

业务文档变化频率低，而查询频率高。离线索引把切块和文档 embedding 的成本移到发布或更新阶段；在线只需要计算查询向量和检索，延迟更低，也避免并发请求重复写索引。

### 56. 为什么选 Chroma？

这个项目是本地演示和个人作品，Chroma 可以嵌入 Python 进程并持久化到目录，不需要单独部署服务，开发成本低。它不代表生产环境的最终选择；如果数据量、并发、权限隔离和高可用要求提高，可以替换成 pgvector、Milvus 或云向量服务，检索接口和索引流程可以保留。

### 57. Chroma 中如何区分业务文档和 Schema？

元数据包含 `kind`。离线业务文档使用 `knowledge_chunk`，实时表结构使用 `schema_table`，查询时用 `where={"kind": ...}` 在向量库侧过滤。这样不会让业务文档向量占满 Schema 的候选列表。

### 58. 实时 Schema 如何同步到 Chroma？

每次 Schema 搜索会对当前表结构 JSON 计算 SHA-256 指纹。指纹变化时，在进程锁内同步 `schema_table` 条目并删除失效 ID；指纹不变则直接复用。锁避免同一进程中的并发请求重复写入，但多进程部署时还需要跨进程协调或把 Schema 索引移到独立更新任务。

### 59. RAG 结果怎样进入模型上下文？

检索工具把完整 Schema 或知识写入 Graph State，ToolMessage 只返回摘要和引用。下一轮由 `AgentContextBuilder` 按预算把 State 投影成模型输入：Schema 最多 65536 token，业务知识最多 32768 token；旧的 Schema ToolMessage 会压缩成表名和 `state.schema` 引用，避免同一份结构重复多次进入上下文。

### 60. 如何评测 RAG？

应建立带黄金表集合、关键字段、连接路径和业务文档 ID 的查询集。离线比较纯 BM25、纯向量和混合 RRF，至少看 Recall@K、MRR、关键关联表完整率和噪声表数量；端到端再看 SQL 执行成功率、结果正确率和平均工具轮数。阈值、Top-K、RRF k 和邻居扩展都应通过这套数据调参。当前 Python 后端还缺这套正式评测，这是明确的后续工作。

### 61. 如何解释“RAG 召回正确但 SQL 仍然错”？

召回只保证模型看到了候选事实，不保证模型正确使用。错误可能来自业务口径冲突、Join 条件选择、时间字段、聚合粒度或模型推理。需要把评测拆成 Schema 召回、业务知识召回、SQL 语法、SQL 执行和结果语义几层，不能只看最终通过率倒推 RAG。

## 五、多轮会话、上下文压缩与记忆

### 62. 多轮对话是怎么实现的？是 ThreadLocal 吗？

不是 ThreadLocal。每条消息都按 `conversation_id` 持久化到 SQLite；新 Run 开始时查询该会话的消息和摘要，构造模型上下文。异步请求可能在不同线程或不同协程执行，连续性来自持久化会话 ID，不依赖某个线程一直存活。

### 63. 为什么不能用 ThreadLocal 保存会话状态？

ThreadLocal 只在当前线程可见，而 FastAPI 协程可能共享线程，阻塞操作也会切到线程池；下一次 HTTP 请求更不保证落到同一线程。它适合保存请求范围的日志上下文，不适合跨请求会话。项目只用 `contextvars` 传播当前 `run_id` 和 LLM 操作名，业务状态仍然显式持久化。

### 64. 当前多层上下文具体有哪些层？

第一层是最近原始消息，保证当前语气和指代；第二层是滚动摘要，压缩更早的会话目标、条件和未解决问题；第三层是按需搜索历史会话和历史分析结果；第四层是用户明确维护的核心记忆，用于跨会话偏好。Graph 内还有当前 Run 的 Tool Call 与 Observation，但它属于任务工作内存，不等于长期会话记忆。

### 65. 什么时候触发滚动摘要？

压力值等于现有摘要 token 加尚未摘要消息 token。达到 `memory_context_token_budget * context_compact_threshold` 才触发。当前记忆预算是 65536 token，阈值 0.8，因此约 52428 token 时开始压缩，而不是固定达到十轮就摘要。

### 66. 摘要时保留多少原始消息？

系统不固定保留三轮，而是按 Token 预算保留最近一段。当前保留预算是记忆总预算的 30%，约 19660 token。摘要器从最新消息往前贪心保留，较早的未摘要消息归档进新摘要。因此消息很短时会保留很多轮，消息很长时保留轮数会变少。

### 67. 滚动摘要如何避免重复摘要同一批消息？

`conversation_summary_state` 保存 `last_message_id` 和累计摘要消息数。下一次只处理这个游标之后的消息；构建最近上下文时也排除游标之前已经被摘要覆盖的消息，避免摘要与原文重复占用 Token。

### 68. 摘要提示词保留什么，删除什么？

保留用户目标、已确认筛选条件和业务口径、重要纠正、已经完成的分析和未解决问题；删除寒暄、SQL 细节和内部提示词。新消息与旧摘要冲突时以用户最新明确表达为准。它的风险是 LLM 摘要可能丢细节，所以最近原文和历史搜索仍然需要保留。

### 69. Token 是如何估算的？

运行时采用本地启发式：非 ASCII 字符按每字一个 Token，ASCII 按约四字符一个 Token。它不依赖具体供应商 tokenizer，适合兼容不同 OpenAI-compatible 模型，但只是保守估算。真实调用后，SDK 返回的 prompt、completion 和 total token 会记录到日志，用于观察估算偏差。

### 70. 为什么不完全依赖模型 API 返回的 usage 决定压缩？

usage 只有请求完成后才能拿到，而是否压缩必须在发送前决定，否则请求可能已经超过上下文。客户端需要本地估算做前置保护，调用后的 usage 用于校准、监控和成本统计，两者作用不同。

### 71. 总上下文上限如何控制？

当前 `max_context_size=200000`。模型请求前会计算 System Prompt、消息和 Tool Schema 的估算 Token；单条超长工具结果先截到 20000 token；整体仍超过 200000 时直接报错，不静默丢掉普通对话。记忆、Schema 和知识分别有 65536、65536 和 32768 token 分区预算。

### 72. 为什么要压缩 ToolMessage？

Schema、查询预览和历史结果可能很大，而且结构化 State 已经保存了完整内容。如果 ToolMessage 再复制一份，Agent 每轮都会重复携带。项目把 Schema 工具结果压成表名、摘要和引用，对单条其他工具结果再做硬截断，减少上下文随循环次数线性膨胀。

### 73. 历史会话如何检索？

SQLite 创建 FTS5 虚拟表，使用 trigram tokenizer 索引会话标题和 user/assistant 消息。Agent 发现用户提到“上次”“以前”或其他会话时，可以先调用 `search_conversation_history` 找候选会话，再用 `read_conversation_history` 读取摘要和最近消息，而不是把所有会话都塞进上下文。

### 74. 历史分析结果如何复用？

每次成功 SQL 的问题、SQL、列名和结果集 ID会写入 `result_history_fts`。Agent 可以搜索当前会话中的历史结果，再按 dataset ID 分页读取。这样用户说“基于刚才结果继续分析”时，不需要重新执行原 SQL，也避免把模型以前的文字总结当成数据库事实。

### 75. 核心记忆如何跨会话？

核心记忆以 profile 为键保存成一份紧凑 Markdown。用户明确要求记住、修改或忘记偏好时，Agent 调用改写工具，LLM基于当前完整记忆进行整块重写；代码检查敏感凭据和 2000 token 上限。创建新会话时，这份内容作为隐藏 System Message 注入。

### 76. 为什么核心记忆采用整块重写，而不是无限追加？

无限追加会产生重复和冲突，也会持续增长。整块重写能保留未修改内容、合并重复偏好，并让模型看到一致的用户画像。风险是一次错误改写可能影响整份文档，因此只有用户明确要求才触发，并设置 Token 和敏感信息限制。

### 77. 当前核心记忆有什么边界问题？

核心记忆更新后，已有会话中的旧隐藏 System Message不会自动更新，新会话才会注入最新版本。另外默认 profile 是全局 `default`，没有真正的用户身份隔离。生产化需要 user_id/profile_id、版本号、审计和冲突控制。

### 78. 自动长期记忆抽取器是怎么设计的？

它让 LLM 输出 upsert/delete 操作，只允许偏好、业务规则、纠正和稳定用户画像；代码再做 key 归一化、空值、重复 key 和最低 0.7 置信度过滤。SQLite 是事实源，可选同步到 Chroma。不过它目前没有接入 Run 完成后的主链，所以这是“已实现组件”，不是“在线自动生效能力”。

### 79. 记忆 TTL 和容量策略是什么？

仓储中实现了默认 180 天 TTL 和单会话最多 500 条的淘汰逻辑，优先考虑类型、重要度和更新时间；但主链目前没有定时或每轮调用 `enforce_memory_retention`。面试时要明确“策略函数已实现，调度尚未接入”，不能说系统已经自动清理。

### 80. 多轮指代消解是单独模型完成的吗？

当前没有独立指代消解节点。近期消息和摘要直接进入 Agent 上下文，模型在工具决策和 SQL 生成时结合它们理解“刚才那个商品”“按月份看”等省略表达。优点是少一次调用，缺点是难以单独评测指代消解准确率。

### 81. 如何测试上下文压缩没有丢掉关键信息？

需要构造长对话测试集，检查摘要是否保留目标、筛选条件、用户纠正和未完成事项；再用压缩前后同一追问比较工具选择与 SQL 结果。代码层测试还应覆盖摘要游标、重复信息、单条超长消息、摘要失败和用户修改旧条件等边界。

## 六、SQL 生成、校验与执行安全

### 82. 为什么 SQL 安全不能只靠系统提示词？

提示词属于概率性约束，模型可能误解、被注入或生成不完整 SQL。SQL 是要访问真实数据库的执行载荷，必须由确定性代码和数据库权限控制。项目用 SQLGlot AST 检查语义结构，再叠加只读会话、执行超时和结果行数限制。

### 83. SQLGlot 在项目中做了哪些检查？

它检查单条 Query、禁止写入和管理 AST、禁止系统库、危险函数和系统变量、禁止 `SELECT *`、校验表字段白名单、要求非 CROSS JOIN 带 ON/USING、拦截敏感字段明细，并对缺失或过大的 LIMIT 自动改写。每项检查会记录到 `checks`，便于前端展示和定位。

### 84. 为什么要用 AST，而不是正则检查 SQL？

正则难以正确处理大小写、注释、子查询、CTE、别名和嵌套表达式，攻击者也容易通过语法变形绕过。AST 把 SQL 解析成表、列、函数、Join 和 Limit 等结构，可以在语法层做确定性判断。正则仍可用于简单字段名规则，但不应承担 SQL 结构安全。

### 85. SELECT-only 如何保证？

先要求 SQLGlot 只解析出一条语句且根节点是 Query，再遍历禁止 Delete、Update、Insert、Create、Drop、Alter 和 Command 等节点。即使用户输入“先 SELECT 再 DROP”，多语句也无法通过。

### 86. 表字段白名单来自哪里？

来自当前 Run 召回并保存在 State 中的实时 Schema。SQL 中物理表必须属于召回表，带表别名的列会映射回真实表校验；无限定字段必须至少存在于某个候选表。这样既拦截不存在字段，也阻止模型访问未召回的其他业务表。

### 87. 表字段白名单会不会误杀？

会。如果 Schema 召回漏表，正确 SQL 也会被判为 `blocked_schema_violation`。因此此类错误标记为可重试，让 Agent 重新检索或查看表结构。CTE 和派生表别名也需要特殊处理，否则派生列会被误判；当前代码已跳过 CTE 引用和派生表列的部分校验。

### 88. 敏感字段如何识别？

配置中维护手机号、邮箱、身份证、薪资、地址、银行卡等关键词。SQL 投影列名做精确或子串匹配；直接返回敏感字段明细会拦截，但 `COUNT` 聚合允许通过。当前是字段名启发式，生产环境更适合由数据目录给字段打敏感等级标签，避免命名不规范造成漏检或误杀。

### 89. 为什么允许对敏感字段 COUNT？

统计数量通常不暴露单个用户明细，例如“有手机号的用户数”。但仅允许 COUNT 仍不够，分组维度太细可能造成重识别。生产环境还需要最小分组人数、脱敏、行列权限和审计，当前实现只覆盖第一层。

### 90. LIMIT 是如何处理的？

如果没有 LIMIT，或字面量 LIMIT 大于配置上限，SQLGlot 会移除原 Limit 并重写为统一上限。当前上限是 50000，而 SQLite 只保存前 50 行预览，完整结果写 CSV。这个上限适合本地分析，但在线服务通常还要根据查询类型分级设置更小上限。

### 91. 为什么禁止 `SELECT *`？

它会无差别读取宽表字段，可能带出敏感数据，也增加网络、内存和模型上下文压力。要求模型只选择必要字段更符合最小权限原则。对于 `COUNT(*)`，AST 形态属于聚合表达式，不应被当成宽表导出误杀，测试需要覆盖这一点。

### 92. JOIN 安全检查是什么？

除显式 CROSS JOIN 外，每个 JOIN 必须有 ON 或 USING，防止模型漏条件产生笛卡尔积。这只能检查“有没有条件”，不能证明条件语义正确，所以还需要真实外键上下文、SQL 执行结果和后续评测。

### 93. 数据库层还有哪些保护？

SQLAlchemy 引擎连接 MySQL时可以执行 `SET SESSION TRANSACTION READ ONLY`，并设置 `MAX_EXECUTION_TIME`、连接读写超时和 `pool_pre_ping`。代码发现使用 root 账号会记录警告。生产环境最关键的是使用只拥有业务表 SELECT 权限的专用账号，因为应用层校验不应成为唯一防线。

### 94. MySQL 访问为什么用了同步 SQLAlchemy，再 `to_thread`？

当前驱动是 PyMySQL，同步反射和查询会阻塞事件循环，所以外层用 `asyncio.to_thread`。这样能保持 FastAPI 主事件循环处理其他请求，但线程池和同步连接池仍有容量限制。更高并发可以切换异步 MySQL 驱动，或独立管理有界线程池。

### 95. 数据库连接池配置是什么？

当前 `pool_size=5`、`max_overflow=5`，理论上单进程最多同时持有约 10 个业务数据库连接。异步 Run 数量没有用信号量限制，如果大量请求同时执行 SQL，任务会在线程池或连接池等待。因此不能把“FastAPI 异步”理解成无限并发。

### 96. SQL 执行失败如何修复？

异常文本写入 `sql_error` 和 observation，Agent 下一轮能看到错误并重新生成 SQL。每次失败累计重试和 SQL 执行计数。真实系统应对错误分类，例如语法错误可修复、权限错误不可修复、超时可缩小范围，避免所有异常都交给模型盲目重试。

### 97. Prompt Injection 如何防护？

输入节点先用规则检测“忽略规则、泄露系统提示、切换角色”等典型模式，命中后在调用 LLM 和 SQL 前直接结束。所有系统提示还声明用户输入、历史消息、检索文档、数据库注释和工具结果均不可信。最后，工具权限和 SQL/Python 安全边界由代码控制，即使提示注入漏过也不能直接获得任意执行能力。

### 98. 规则型 Prompt Injection 检测有什么问题？

正则容易误杀正常安全讨论，也可能被同义改写、编码或跨语言绕过。它适合作为低成本前置层，不是完整解决方案。更完善的方案包括规范化输入、风险分类器、数据与指令分隔、工具最小权限、输出泄露检测和红队评测。

### 99. 用户说“不要 LIMIT，查询全部订单”，系统应该怎样处理？

模型即使生成无 LIMIT SQL，AST 策略也会自动加上统一上限。因此可以安全返回有限结果，而不一定必须完全拒绝。评测时应以“危险意图没有造成无限导出”为目标，而不是只接受某一个 result mode。

### 100. 如何证明 SQL 没有幻觉？

无法绝对证明，但可以分层降低风险：Schema 来自实时反射；执行前校验表字段白名单；业务口径来自检索文档；只读执行让不存在字段直接失败；结果总结只能引用真实结果集 ID。最终仍需用黄金 SQL、结果签名和人工标注评测语义正确性。

## 七、Python 分析与大结果集管理

### 101. 为什么有 SQL 还需要 Python 分析？

SQL 擅长过滤、Join 和聚合，但异常检测、相关性、多结果集合并和较复杂的时间序列计算用 Pandas 更灵活。项目让 SQL 先缩小数据范围并得到真实结果，再由 Agent 判断是否调用 Python，避免一开始就把全库数据交给生成代码。

### 102. Python 代码是谁生成的？

LLM 根据分析目标、数据集列、行数和少量样例生成完整脚本。脚本读取固定路径下的 CSV，并把指标、发现、图表和摘要写到固定的 `result.json`。生成结果先经过 Pydantic 结构校验和 Python AST 静态检查，再进入容器。

### 103. Python 静态安全检查包括什么？

只允许标准统计模块、NumPy 和 Pandas；禁止 `eval`、`exec`、`compile`、`__import__` 等危险调用；禁止访问双下划线属性；`open` 只能访问约定输入和输出文件，动态文件路径直接拒绝。静态检查不是完整沙箱，因此后面仍要依赖 Docker 隔离。

### 104. Docker 沙箱有哪些限制？

每次分析启动一次性容器，关闭网络，根文件系统只读，丢弃全部 Linux capabilities，禁止获取新权限，以 UID/GID 65534 运行，限制 512 MB 内存、1 个 CPU、64 个 PID、30 秒超时，`/tmp` 使用不可执行的 tmpfs。输入和代码只读挂载，只有输出目录可写。

### 105. 为什么静态检查和 Docker 都要有？

静态检查能在启动容器前快速拒绝明显危险代码，也能给模型明确错误用于修复；Docker 是运行时隔离，即使 AST 检查漏掉某种语法技巧，也限制网络、文件、权限和资源。两层防护解决不同问题，不能互相替代。

### 106. Python 分析失败如何处理？

语法、策略、执行或结果格式失败后，服务把错误尾部回传给模型重新生成，当前最多修复 2 次，也就是总共尝试 3 次。每次代码、解释、日志和结果会形成 Python Analysis Artifact。连续失败则显式抛出沙箱错误，不生成虚假分析结果。

### 107. 为什么完整结果存 CSV，SQLite 只存预览？

SQLite 适合保存会话元数据和小型 JSON，不适合频繁写入大量结果行。全量 CSV 便于流式写入、分页读取、导出和只读挂载给容器；SQLite 保存列信息、总行数、前 50 行预览和文件路径，前端和模型大多数时候只读少量数据。

### 108. CSV 写入如何避免半文件？

先写同目录临时文件，完成后用 `os.replace` 原子替换目标文件。如果 SQLite 提交失败，再删除已经生成的 CSV，尽量保证数据库记录和文件状态一致。

### 109. 结果集如何分页？

API 根据页码计算 offset，从 CSV 使用 `islice` 读取指定范围，并按列元信息恢复整数、浮点和布尔类型；单页最大 500 行。文件过期后只能读取 SQLite 中的预览，接口会标记截断，不能假装还有完整数据。

### 110. 结果文件多久清理？

默认 TTL 为 168 小时，也就是 7 天；数据目录总配额 512 MB。清理先删除过期文件，仍超配额时按创建时间从旧到新淘汰。数据库记录不会删除，而是把存储类型改成 SQLite，只保留预览和“已截断”状态。

### 111. 当前 512 MB 配额实现有什么细节？

同一个配置既用于单个文件上限，也用于数据目录总上限，因此单文件理论上可以占满全部配额。更合理的生产配置应拆成单文件限制与总目录限制，并增加用户或租户配额。

### 112. 为什么模型最终只读取最多 50 行结果？

最终总结阶段会为每个结果集读取最多 50 行作为证据，同时携带总行数和列信息；复杂全量计算交给 SQL 或 Python。这样避免几万行数据直接进入 LLM。代价是如果 SQL 没有先聚合，模型不能仅凭前 50 行正确总结整体分布，因此提示和工具策略必须要求先做合适聚合。

### 113. 如何防止模型在总结时编造图表字段？

结果提示要求指标、发现和图表引用实际 resultSetId，代码会把所有查询结果的列作为合法字段集合，对输出做规范化；持久化前再次校验来源 ID，单结果时可以补默认来源，多结果时只保留有效来源。Python 分析结果也会限制图表类型和最多 1000 行内联数据。

### 114. 为什么不能把完整结果直接放进 SQLite JSON？

大量 JSON 会放大 SQLite 写锁、数据库体积和序列化成本，也不利于按页读取。CSV 的缺点是缺少事务、类型信息有限、随机分页越靠后越慢；如果数据规模继续增大，可以改为 Parquet 或对象存储，并把元数据继续留在 SQLite/PostgreSQL。

## 八、FastAPI、SSE、异步与持久化

### 115. 项目是基于 Flux 还是 SSE？

Python 后端没有 Reactor Flux。内部使用 Python 异步生成器和 `asyncio.Task`，对外通过 FastAPI `StreamingResponse` 输出 `text/event-stream`，协议是 SSE。Flux 是 Java 响应式流类型，SSE 是 HTTP 上的事件传输协议，二者不是同一层概念。

### 116. SSE 为什么适合这个项目？

分析过程主要是服务端单向推送阶段、工具和结果事件，客户端提交问题和审核可以走普通 REST。SSE 基于 HTTP，浏览器支持自动重连和 `Last-Event-ID`，实现成本比 WebSocket 低。若未来需要高频双向协作或二进制流，再考虑 WebSocket。

### 117. SSE 是直接从内存 Sink 推送吗？

不是。Graph 执行器先把事件持久化到 SQLite，SSE 端点每 0.1 秒查询序号大于游标的新事件，再输出给客户端。这样前端即使晚连接或中途断线，也能从数据库补发；代价是有轮询延迟和额外数据库读取。

### 118. SSE 如何断线续传？

每个事件有递增 sequence，SSE 帧把它写入 `id`。客户端重连会携带 `Last-Event-ID`，也可以显式传 `after_seq`。服务端从该序号后查询事件，因此不会从头重放。没有新事件时每 10 秒发送心跳注释维持连接。

### 119. 当前是真正的 Token 级流式输出吗？

不是。LLM 使用 Chat Completions 非流式请求，SSE 实时展示的是阶段、工具、产物和最终摘要事件；`text.delta` 当前一次发送完整摘要，不是逐 Token。简历可以写“实时返回分析过程”，不要说“模型逐字流式输出”。

### 120. `asyncio` 是否等于多线程？

不等于。FastAPI 的异步路径主要在单事件循环中通过协程切换处理 I/O；同步 MySQL、Schema 反射、Chroma 查询和文件读写通过 `to_thread` 进入线程池；Docker 用异步子进程。一次请求可能跨协程、线程和子进程，不能假设始终使用同一线程。

### 121. 哪些操作会切换线程？

`BusinessDatabase.schema_snapshot/execute_select`、混合检索和向量检索、CSV 写入与分页读取等使用 `asyncio.to_thread`。LLM SDK 和 SQLite AsyncSession主要是异步 I/O；Docker 使用 `asyncio.create_subprocess_exec`。日志中的 `contextvars` 用来在协程上下文传播 Run ID，不是业务状态容器。

### 122. TaskRegistry 如何工作？

它是进程级 `dict[run_id, asyncio.Task]`。相同 Run 已有活跃任务时关闭新协程，避免重复执行；任务完成后 callback 自动从 Map 删除；取消或服务关闭时会取消并等待任务结束。它只适合单进程本地部署，不是分布式任务队列。

### 123. 当前并发控制有什么不足？

TaskRegistry 不限制不同 Run 的总数量，也没有排队、优先级和背压。大量请求会同时发起 LLM、线程池任务和数据库连接等待。生产化应增加有界 Semaphore 或任务队列，并分别限制 LLM、SQL 和 Python 容器并发，结合 RPM/TPM 做限流。

### 124. 为什么选择 SQLite 保存应用状态？

项目定位是本地单机演示，SQLite 零部署、事务和 SQL 查询能力足够，配合 SQLAlchemy 能保存会话、运行、事件、审核和结果元数据。开启 WAL、5 秒 busy timeout 和外键后，可以应付有限并发。多实例部署时则需要 PostgreSQL 等共享数据库。

### 125. SQLite WAL 有什么作用？

WAL 模式让读操作不必等待写事务完全结束，提高读写并发；但 SQLite 仍然只有一个写者，高并发写事件时可能争锁。`busy_timeout=5000` 只是在锁冲突时等待，不会从根本上提升写吞吐。

### 126. 为什么历史搜索用 SQLite FTS5？

历史消息和结果已经在 SQLite，本地场景没必要再复制到向量库。FTS5 trigram 支持中文子串和模糊搜索，延迟低、维护简单。它不具备语义同义词能力，所以 Agent 找不到时可能需要更宽松关键词或后续引入 embedding 索引。

### 127. 如何保证创建 Run 的幂等性？

客户端可传 `idempotency_key`，创建前查询已有 Run，命中则直接返回，不重复写消息和启动任务。人工审核决策也检查 Review 是否仍为 waiting，重复提交不会再次恢复图。

### 128. 删除会话时如何避免后台任务继续写数据？

先遍历该会话未终态 Run，调用 `cancel_and_wait` 等任务真正结束，再删除会话及关联数据，并从可选记忆向量索引中删除记忆 ID。这个顺序避免产生孤儿任务继续写已删除会话。

### 129. 服务重启后悬挂任务如何处理？

启动时查询 `queued/running` Run，统一标记为 `service_restarted` 失败并提示重试。这样前端不会永远显示运行中，但任务不能自动续跑。要实现真正恢复，需要持久化任务队列、幂等工具执行和按 checkpoint 判断安全重放。

## 九、LLM 客户端、可靠性与可观测性

### 130. 为什么使用官方 OpenAI SDK？

项目接入的是 OpenAI-compatible 模型，官方异步 SDK已经处理连接、超时、重试、错误类型、Tool Calling 和 usage，比手写 HTTP 更稳定。上层通过自定义 `LlmClient` 端口隔离，未来替换供应商时不需要改工作流节点。

### 131. 模型输出如何做结构化校验？

分析结果、摘要、核心记忆和 Python 代码等用 Pydantic 模型定义。客户端从模型文本提取 JSON 后调用 `model_validate_json`，缺字段或类型错误就显式失败，不把错误结果伪装成成功。原生工具调用参数也必须解析成 JSON 对象。

### 132. 模型输出到达 Token 上限时怎么办？

SDK 返回 `finish_reason=length` 时直接抛出“输出不完整”错误，不接受被截断 JSON。调用前还会估算输入总 Token，超过上限直接拒绝。更完整的方案可以按输出类型设置 `max_completion_tokens` 和重试策略，但不能对残缺结果静默补默认值。

### 133. 当前 LLM 重试参数合理吗？

`max_retries=20` 对本地调试过高，供应商持续失败时会显著放大延迟。应该只对 429、连接错误和部分 5xx 使用指数退避，并限制总重试时间；401、参数错误和结构化输出错误不应交给 SDK重复请求。

### 134. 项目如何记录 LLM 可观测性？

每次调用记录 runId、操作名、模型、Base URL、估算输入 Token、请求 ID、finish reason、实际 prompt/completion/total token 和耗时。可选记录经过字符上限截断的模型输入、工具 Schema、输出和工具调用参数。API Key 不写日志。

### 135. 日志中记录完整 Prompt 有什么风险？

可能包含业务数据、用户消息、SQL 和结果预览，存在隐私与合规风险。当前默认开启原始响应和 I/O 日志适合本地调试，不适合生产。生产应默认关闭正文，保留结构化指标，并对敏感字段脱敏、限制访问和设置日志保留期。

### 136. 如何追踪一条请求？

HTTP 层生成或沿用 `X-Request-ID`，Run 级日志使用 `run_id`，LLM 操作名通过 `contextvars` 传播。数据库还保存 Stage、ToolCall、Artifact 和 RunEvent，因此可以从请求、运行、节点、工具到最终产物逐层定位。

### 137. 为什么事件要先落库再通过 SSE 推送？

持久化事件让前端断线后能重放，也让“过程”成为可审计数据，而不是只存在于某个连接内。缺点是 SQLite 写放大和轮询延迟。高并发生产系统可采用事务内 Outbox，再通过 Redis Stream、Kafka 或专门事件服务推送。

### 138. 错误如何暴露给前端？

未捕获异常会把 Run 标记为 failed，保存异常类型、消息和耗时，同时补全未完成 ToolCall 与 Stage 状态，并写 `run.failed` 事件。安全拦截则是正常完成但带明确 result mode，与基础设施异常区分。

### 139. 当前错误处理有什么值得改进的地方？

`GraphAnalysisExecutor._consume` 捕获所有异常并转成失败 Run，这对后台任务是必要的，但调用栈不会继续向任务外抛出；必须依赖日志和 Run 状态观察。部分工具会把异常包装成 `ok=false` observation。后续应建立错误分类和告警，明确哪些可由 Agent 修复、哪些必须立即终止。

### 140. 如何监控成本和延迟？

可以按 Run 汇总 LLM 调用次数、输入输出 Token、各阶段耗时、工具次数、SQL耗时、Python 容器耗时、重试次数和最终状态。当前日志已有单次 LLM token/耗时，Stage 也有 duration，下一步应写入指标表或接入 OpenTelemetry/Langfuse，形成 P50/P95 和单任务成本看板。

## 十、测试、评测与质量保障

### 141. 当前测试覆盖哪些内容？

测试覆盖 FastAPI API 契约、LangGraph 工具流程、人工审核恢复、会话 CRUD、SQL 安全、提示注入、RAG、中文 BM25、Schema 邻居扩展、增量索引、上下文摘要、核心记忆、LLM SDK、Token 上限、结果序列化、历史结果、Python 分析和日志。集成测试使用确定性 Fake LLM 和临时 SQLite，避免依赖真实模型。当前完整测试结果为 89 项通过。

### 142. 为什么测试不用真实 LLM？

真实模型输出有随机性、成本和网络依赖，不适合每次提交的回归测试。Fake LLM可以验证图路由、工具顺序、状态持久化和 API 契约。真实模型能力仍需要独立离线评测和少量端到端冒烟测试，两者不能相互替代。

### 143. 应该怎样测试 SQL 安全？

使用参数化用例覆盖 DELETE/UPDATE、多语句、系统表、危险函数、`SELECT *`、未知表字段、无条件 JOIN、敏感字段、COUNT 聚合和 LIMIT 改写；再做变形测试，例如大小写、注释、CTE、子查询、别名和嵌套函数。通过测试必须验证返回的规范化 SQL，拦截测试必须验证 result mode 和 retryable。

### 144. 应该怎样评测自然语言到 SQL？

不能只做字符串相等。先比较 SQL 是否可执行，再比较结果集签名或结果内容；对危险/澄清类问题看是否避免不当执行；对多步分析看最终目标是否完成。黄金 SQL只用于辅助，因为不同 SQL 可能得到相同正确结果。

### 145. RAG 消融实验怎么做？

固定同一模型、提示词、数据库和查询集，只切换纯 BM25、纯向量、BM25+向量+RRF，再分别关闭外键邻居扩展。记录表召回 Recall@K、关联链完整率、业务文档命中率、SQL执行成功率、结果正确率、平均上下文 Token 和延迟，至少重复运行降低模型波动。

### 146. 如何评测多轮记忆？

设计条件延续、指代、用户纠正、话题切换后回切、跨会话偏好和长对话压缩六类用例。分别检查模型是否继承正确条件、是否用最新纠正覆盖旧条件、是否错误带入其他话题，以及压缩前后答案是否一致。

### 147. 如何评测 Python 分析？

使用固定 CSV 和确定性目标，检查生成代码是否通过策略、结果 JSON 是否符合结构、数值是否与本地黄金计算一致、超时和危险代码是否被拦截。不能只看脚本成功退出，因为它可能生成格式正确但数值错误的结果。

### 148. 为什么需要端到端 API 测试？

单元测试能验证组件，但项目的风险集中在组件衔接：ToolCall 是否持久化、SQL 是否一定经过校验、人工审核是否恢复同一 Run、SSE 是否能看到终态、结果集 ID 是否正确引用。端到端测试用真实 LangGraph 和 SQLite、Fake LLM验证这些契约。

### 149. 当前还缺什么测试？

缺真实模型离线评测、并发压力、SQLite 锁冲突、服务重启后的 checkpoint 行为、Chroma 多进程同步、Docker 逃逸红队、超大 CSV 分页性能和长期运行磁盘清理测试。自动长期记忆组件也需要接入主链后再补端到端测试。

## 十一、常见基础知识追问

### 150. 协程、线程和进程在本项目中分别做什么？

协程负责 FastAPI 请求、LLM I/O、SQLite I/O 和任务编排；线程承接同步 MySQL、Chroma 和文件操作，避免阻塞事件循环；独立 Docker 进程执行不可信 Python 代码，提供更强资源与权限隔离。三者分别解决高并发 I/O、兼容同步库和安全隔离问题。

### 151. Python 有 GIL，`to_thread` 为什么仍有价值？

数据库和文件操作大部分时间在等待 I/O，底层库也可能释放 GIL，因此线程能让事件循环继续处理其他请求。对于纯 Python CPU 密集计算，线程不能有效利用多核，所以项目把复杂数据分析放到独立 Docker 进程。

### 152. `asyncio.create_task` 有什么风险？

任务生命周期属于当前进程，进程崩溃就丢失；未持有引用可能被回收或异常无人观察；无限创建会耗尽资源。项目用 TaskRegistry 持有引用、自动清理和取消，但仍缺持久队列与总并发限制。

### 153. Pydantic 在项目中承担什么作用？

一方面校验 FastAPI 的请求与响应契约，另一方面校验 LLM 结构化输出，防止缺字段和错误类型继续流入工作流。它保证结构合法，不保证业务内容正确，所以数值和 SQL 仍需独立校验。

### 154. Repository 模式的价值是什么？

应用层不直接拼 ORM 查询，而通过 Repository 管理会话、Run、事件、结果和审核。这样事务和 SQLite 特有 FTS逻辑集中，测试也更容易替换。当前 `Repository` 聚合的职责较多，继续增长时可以按会话、运行、结果拆分更明确的接口。

### 155. 什么是背压？当前项目有吗？

背压是下游处理不过来时限制上游生产速度。当前 SSE 通过数据库轮询天然不会把事件无限塞进单个内存队列，但 Run 创建和 LLM/SQL/Python 执行没有总并发背压。需要队列长度、Semaphore、拒绝策略和限流共同解决。

### 156. 为什么 API 返回快照和 SSE 两套接口？

SSE 适合增量过程，但不适合承担唯一事实源；客户端错过事件或刷新页面时，需要 Run 快照恢复完整页面。事件回答“发生了什么”，快照回答“现在是什么状态”，两者组合比只依赖长连接稳定。

### 157. 事务一致性如何考虑？

单次 Repository 写操作通常提交 SQLite 事务；CSV 先原子落盘，再提交结果记录，提交失败会删除文件。但跨数据库、文件和事件没有全局事务，仍可能出现进程在中间崩溃。可以通过状态机、补偿清理和 Outbox 缩小不一致窗口。

### 158. 为什么不用 Redis 保存会话？

本地单机项目需要历史会话、全文检索、审核、结果和事件审计，SQLite 的持久化与查询能力更合适。Redis 更适合缓存、分布式锁、限流和短期状态；生产部署时可以用 PostgreSQL做事实源，Redis做热点缓存和任务协调。

### 159. 如果改成多实例部署，哪些地方会出问题？

进程内 TaskRegistry 不共享；SQLite 和本地 CSV/Chroma 不能被多实例可靠共享；Schema 指纹锁只在单进程有效；SSE 查询的事件库也必须共享。需要外部任务队列、PostgreSQL、对象存储、独立向量服务、分布式限流和统一可观测平台。

### 160. 如果数据量从 5 万行增长到千万级，怎么改？

尽量让数据库先聚合，只把小结果交给 Agent；为业务查询建立索引和只读副本；完整明细用对象存储或 Parquet，不在应用内一次性加载；Python 分析改为分布式或受控计算服务；结果分页使用游标或数据库查询，不再线性扫描大 CSV。

## 十二、设计取舍、缺陷与改进

### 161. 你认为当前项目最好的设计是什么？

我认为是把模型决策和确定性执行边界分开。Agent 可以灵活选择检索和分析步骤，但 SQL 必须经过固定图节点校验，Python 必须经过 AST 与容器隔离，结果必须引用持久化数据集。这样保留了 Agent 的灵活性，又避免把关键安全职责交给模型。

### 162. 当前最大的架构不足是什么？

运行调度仍是单进程内存 Task，没有总并发、任务队列和崩溃续跑；同时部分记忆组件已实现但未接入主链，文档与配置也存在不一致。它作为本地作品可以运行，但离真正多租户生产系统还有明确距离。

### 163. 当前 RAG 最大的问题是什么？

缺少正式评测和调参证据。Top-K、向量阈值、RRF k 和一跳邻居扩展都有明确实现，但目前主要是经验值。下一步应先建立 Schema 与业务知识黄金集，再决定是否加入 reranker 或图搜索，而不是继续堆检索组件。

### 164. 当前记忆系统最大的问题是什么？

摘要和显式核心记忆已经在线生效，但自动长期记忆抽取、检索和 TTL 没接主链，接口字段却已经预留，容易让人误以为完整功能已经工作。应先完成主链接入、用户隔离、调度与端到端测试，再在简历中扩大表述。

### 165. 当前安全系统最大的问题是什么？

提示注入检测仍然是规则型，敏感字段依赖名称关键词，SQL 白名单依赖召回 Schema；这些都可能误杀或漏检。数据库最小权限、审计、数据分级和红队评测还需要补齐。Docker 沙箱也应增加 seccomp/AppArmor 等更强策略。

### 166. 为什么当前 50 次 Agent/SQL 上限不合理？

虽然防止了真正无限循环，但一次异常任务可能产生大量模型调用和数据库查询。校招面试中我会主动说这是调试阶段放宽的配置，合理生产值应按简单和复杂任务分级，例如 6 到 12 轮、2 到 5 次 SQL，并设置总 Token、总耗时和取消机制。

### 167. 如果只允许做三项改进，你会选什么？

第一，建立覆盖 Schema、业务口径、SQL 结果和安全场景的离线评测，先获得可量化基线。第二，引入有界任务队列和分资源并发限制，解决单进程任务堆积。第三，完成长期记忆主链接入与用户隔离，删除未生效的虚假状态字段或让它们真正工作。

### 168. 为什么不直接上多 Agent？

当前任务的工具边界清楚，一个 Agent 加确定性工作流已经能完成大多数查询。多 Agent 会增加角色协调、上下文复制、延迟和错误归因难度。只有当规划、数据工程、统计分析等子任务具备独立上下文、工具和评测标准时，拆分才有收益。

### 169. 工作流和 Agent Loop 应该如何取舍？

固定、安全、可验证的步骤用工作流，例如输入检查、SQL 校验、审核和执行；需求不确定、需要根据观察动态选择的步骤用 Agent Loop，例如检索哪张表、是否继续查询、是否调用 Python。项目采用混合结构，而不是在两者中二选一。

### 170. 如果模型更换，哪些地方要重新验证？

Tool Calling 兼容性、结构化 JSON稳定性、上下文窗口和 thinking 参数；Embedding 更换后必须重建 Chroma，并重新调向量阈值；生成模型更换后要回归 SQL、工具选择、摘要、长期记忆和 Python 代码安全。不能只改模型名就认为行为一致。

### 171. 如果面试官问“这是你独立完成的吗”，怎么回答？

应按真实情况回答。我会说自己负责 Python 后端的架构与主要实现，包括 LangGraph 工具循环、检索、上下文、SQL 安全、结果存储和 Python 沙箱，并说明哪些设计参考了外部资料或使用了开发工具辅助。面试官真正会继续确认的是关键取舍、排查过程和你对代码边界的理解。

### 172. 项目中遇到过什么典型问题？

可以讲一次“表信息没有进入模型导致 SQL 幻觉”的问题。排查后发现模型输入组装缺少可靠的 Schema 工具链，单改 Prompt 解决不了。最终把实时 Schema 检索注册为工具，增加无 Schema 禁止执行的代码护栏，并用 SQLGlot 表字段白名单兜住，即使召回或模型选择出错也不会执行不存在字段。

### 173. 再举一个有工程价值的问题。

可以讲“大结果集直接进入上下文导致慢和不稳定”。我的处理方式是分层保存和使用数据：SQL 负责聚合，完整结果 CSV 落盘，SQLite 存预览和引用，模型只按需读取少量行，复杂全量计算交给 Docker Python。前端分页、导出和 Python 分析也复用同一份结果文件。

### 174. 如果面试官质疑项目过度设计，怎么回答？

我会承认本地销售演示库不一定需要所有组件，但设计是围绕几个真实问题逐步增加的：人工审核需要 checkpoint，断线回看需要持久化事件，大结果需要文件存储，生成代码需要隔离。也有尚未收敛的地方，例如记忆组件未完全接入、默认循环上限过大，这些正是我会继续删减和完善的部分。

## 十三、简历逐条追问

### 175. “解决选错表、漏关联表和编造字段”分别靠什么？

选错表主要靠 BM25+向量+RRF 的 Schema 召回；漏关联表靠外键邻居扩展和 `inspect_tables`；编造字段靠实时 Schema 上下文与 SQLGlot 字段白名单。前两项提高生成质量，最后一项负责执行前阻断，不能混成一个单一技术点。

### 176. “解决多轮上下文断裂”具体靠什么？

跨请求消息全部按会话持久化；每次 Run 构建近期原始对话和滚动摘要；提到过去会话或历史结果时，由 Agent 调用 FTS5 搜索和读取工具；用户明确的跨会话偏好写入核心记忆。不是依赖 ThreadLocal，也不是简单把全部历史拼接进 Prompt。

### 177. “降低字段幻觉”为什么不能写“消除字段幻觉”？

召回可能漏表，模型也可能在未覆盖的表达式或派生结构中出错。白名单能拦截大量不存在字段，但不能证明业务语义正确，所以只能说降低或拦截风险，不能说完全消除。

### 178. “避免大结果集直接进入模型上下文”具体怎么做到？

MySQL结果上限控制；完整数据写 CSV；Graph State 只保存结果引用和最多 50 行预览；活动结果默认只给 Agent 20 行；最终总结每个结果最多读 50 行；单条 ToolMessage 最多 20000 token；复杂全量统计交给 Python 沙箱。

### 179. “支持自然语言分析销售额、订单趋势、商品表现、用户消费和库存”底层数据有哪些？

演示库包含 users、categories、products、promotions、orders、order_items 和 refunds 七张表。用户和订单带地区、会员、渠道等维度；订单明细保存下单时价格与成本快照；业务文档定义 GMV、销售额、退款等口径，为跨表和历史指标分析提供依据。

### 180. 项目介绍中为什么写“按需调用工具”？

因为模型不是每次固定执行所有阶段。普通聊天可以直接结束；简单数据查询可能只查 Schema 后执行一条 SQL；业务口径问题会额外检索知识；复杂任务可以多条 SQL 后调用 Python；历史追问可以读取旧结果而不重查数据库。执行路径由当前观察动态决定。

## 十六、面试时不要说错的十件事

1. 不要说项目有独立意图识别节点，当前是统一 Agent Tool Loop。
2. 不要说使用了独立 rerank 模型，当前是 RRF 融合排序。
3. 不要说 SSE 是模型逐 Token 输出，当前主要流式返回阶段和持久化事件。
4. 不要说 `thread_id` 是操作系统线程 ID，它只是 LangGraph 运行标识，当前值为 `run_id`。
5. 不要说 checkpoint 负责跨轮会话记忆，跨轮由 SQLite 消息与摘要负责。
6. 不要说服务重启后所有运行会自动续跑，当前 running/queued 会标记失败并要求重试。
7. 不要说自动长期记忆已经完整在线生效，当前主链未调用抽取、检索与 TTL 淘汰。
8. 不要说 SQL 安全仅靠 Prompt，核心是 SQLGlot AST、只读会话和数据库权限。
9. 不要说最多只能四表联查，四张是初始 Top-K，外键扩展后最多八张，还能继续查看表。
10. 不要引用没有在 Python 后端评测中得到的召回率、SQL 正确率或提升百分比。

## 十七、推荐的面试回答节奏

第一句先回答结论，例如“这里用 conversation_id 标识会话，状态持久化在 SQLite，不依赖 ThreadLocal”。第二层讲关键实现，例如“Run 开始时组合近期消息与摘要”。第三层再讲取舍，例如“因此可以跨请求，但多实例要把 SQLite 和本地文件替换为共享存储”。

遇到当前项目确实没完成的地方，直接说明边界并给出下一步方案，比把未接入组件说成已经上线更可信。面试时应把模型决策、确定性安全边界、持久化状态和可恢复交互讲成一条完整的数据流，框架名称只用于解释具体实现。
